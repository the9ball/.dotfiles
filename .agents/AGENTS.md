## Local project instructions

- When an `AGENTS.md` exists in a directory, read `AGENTS.local.md` in the same directory as additional instructions when that file exists.
- AIツールがスクリプトを書く際は、内容を読んで実行を許可してよいか判断しやすくするため、変数名・関数名・コマンド引数などに短縮名（略語・頭字語）をなるべく使わず、意味が明確な名前を使う。

## サブエージェントへの委譲

- サブエージェントを使える環境では、下記の「委譲が不利なケース」に当たらない限り積極的に委譲する。迷ったら委譲する側に倒す。狙いは、調査や定型作業を委譲先に寄せ、主スレッドのコンテキストを判断そのものに使うこと。
- 委譲が不利なケース(委譲しないほうがよい):
  - 主スレッドが一度の短い作業で終えられ、引き継ぎ・統合・結果検証のほうが重い。
  - 途中でユーザーの判断・承認を繰り返し必要とし、委譲先が独立して進められない。
  - 自己完結した引き継ぎに必要な文脈が、作業そのものと同程度以上になる。
  - 委譲先から必要なファイル・ツール・認証・実行環境に届かない、または機密情報を安全に渡せない。
- 委譲するときは、目的・対象・対象外・制約、完了条件、検証方法、見積り超過を含む停止・確認条件を、それだけで作業できる形で渡す。委譲先は、呼び出し側の会話を前提にできない。
- 委譲は権限も承認範囲も広げない。「スレッド取り違えの確認」を先に済ませ、「ファイル変更前の範囲確認」の承認前に委譲してよいのは読み取り専用の作業だけ。委譲先による変更も承認済みの範囲に限る。「一つずつ」「順番に」の指定がある作業は並行させない。
- 同じ作業ツリーに書き込む場合は、ファイル単位で編集の担当を一つに限る。分けられないなら、委譲先の完了まで主スレッドは同じ範囲を触らない。
- 委譲先を選べる場合は、タスクを十分遂行できる範囲で最も低コストのモデルを優先する。より高性能なモデルは、成功率や品質の改善が見込める場合に限り使用する。
- エージェント定義側が「自動起動しない」「明示的な指名を待つ」と定めている場合は、この既定より定義側を優先する。
- 委譲先の報告を鵜呑みにしない。ファイル変更や検証結果など事実に関わる結論は、自分で差分やログを確認して裏を取る。

## 用途別ガイドの参照

- `~/.dotfiles/.agents/guides/` には、特定の作業に入るときだけ読む詳細な指針を置く。本ファイルの項目が参照を指示している場合は、その作業を始める前に該当ファイルを読む。
- 用途別ガイドは本ファイルを補足するものとして扱う。本ファイルと矛盾する場合は本ファイルを優先する。

## ファイル変更前の範囲確認

- 編集前に変更対象・内容・対象外を短く提示し、明示的な承認を得る。具体的な依頼でも復唱と承認を省略しない。
- 承認前は読み取り専用の調査・テスト・変更案作成のみ行ってよい。承認範囲を超える場合は再承認を得る。
- 承認済みの計画に変更範囲が明記されている場合、再確認は不要。
- 「一つずつ」「順番に」は、項目ごとに変更・検証・報告してから次へ進む。

## 実装規模の見積り

- 実装計画を作る規模のタスクでは、要素ごとに推定コード量(行数)をソフト目標として計画に書く。実装中に見積りを大きく超えた場合(1.5倍かつ+30行以上が目安、範囲で見積った場合は上限を基準)は作業を止め、超過理由と対応案をユーザーに報告する。自分で妥当性を判断して続行してはならず、ユーザーの明示的な承認を得てから続行する。
- 要件はハード目標、コード量はソフト目標。コード量に収めるために要件・エラーハンドリング・ガード節を落とすこと、および可読性を損なう圧縮(1行への詰め込み、中間変数の削除、命名の短縮)は禁止。
- 詳細は `~/.dotfiles/.agents/guides/implementation-planning.md` を読む。

## JSON ファイルの参照

- JSON ファイルの値を調べる・抽出するときは、テキスト検索(grep / ripgrep / Select-String)ではなく、構造を解釈できるツールを使う。
- 使うツールは環境に合わせて選ぶ。PowerShell が使える環境（Windows など）では標準搭載の `ConvertFrom-Json` を優先し、Unix 系で `jq` が使える環境では `jq` を使う。どちらも使えるなら好みでよい。
- grep 系はキー名や構造にまたがる検索で取りこぼし・誤ヒットが起きやすいため、JSON に対しては原則使わない。ファイル全体をテキストとして眺めたい場合など、明確な理由があるときだけ例外とする。

## .NET テスト実行

- `dotnet test` がビルド込みでタイムアウトしやすいため、実装後のテストは原則として `dotnet build` と `dotnet test --no-build` の2段階で実行する。
- build と test の構成が一致するよう、必要に応じて両方に `-c Debug` など同じ構成を指定する。
- `dotnet build` と `dotnet test` を実行する際のツール側タイムアウトは、I/O などによる一時的な遅延を考慮して原則5分（`300000ms`）にする。

## Markdown コードフェンス

- AIがユーザーとのチャット応答で、ユーザーがコピーして利用するためのコードブロックを提示する場合は、開始・終了ともに必ず U+0060（バッククォート）を5個連続して使う。
- そのようなコードブロックを含むチャット応答を送信する前に、コードフェンスが正しく閉じていることを確認する。

## 他エージェントへ渡す文面の出力

- ユーザーが他のエージェントへ中継するための文面(依頼文・調査指示・レビュー観点など)を求めた場合は、渡す本文全体をコードブロック1つに入れて出力する。ユーザーがコピーする範囲を判断しなくて済むようにするため。
- 見出しやセクションごとにブロックを分けない。文面が長くても1つにまとめる。
- コードブロックには渡す本文だけを入れる。前置き・補足・こちらの判断や注意書きはブロックの外に書く。
- 本文は Markdown で書く。外側のフェンスは「Markdown コードフェンス」のとおりバッククォート5個とし、開始側に言語指定 `markdown` を付ける。本文中にコードブロックを含める場合は内側を3個にする。
- 特定のエージェント名を前提にした書き方はしない。渡す先が変わっても使えるよう、宛先に依存しない文面にする。

## スレッド取り違えの確認

- この会話にない直前の作業・判断・結果を前提としていて、依頼単独では対象や期待する状態を確定できない場合に限り、着手前に宛先を確認する。自己完結した新規依頼や単なる話題の変更では発動しない。迷ったら発動しない側に倒す。
- 非発動時は、この確認ルールの判定を説明せず、通常の応答・手順に進む。
- 確認の返答を得るまでツールを使わない(ファイル変更・コマンド実行・外部送信を含む)。候補スレッドを自分で探しに行かない。
- 確認するときは次の一文だけを出力する。前置き・補足・理由説明を一切付けず、依頼の対象名(ファイル・機能・チケット番号など)にも触れない。
  - 「この会話にない直前の作業を前提としているように見えます。このスレッド宛で合っていますか。」
- 取り違えが確定したら、このスレッドでは作業せず停止する。正しいスレッドから改めて依頼してもらう。該当スレッドを探したい場合は、別セッションを立てて探すよう案内する。
- 「合っている」と答えられたら、同じ対象と前提が続く限り再確認しない。
- この確認は「ファイル変更前の範囲確認」より前に行う。宛先確認への回答は変更承認を兼ねない。
