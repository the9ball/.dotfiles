## Local project instructions

- When an `AGENTS.md` exists in a directory, read `AGENTS.local.md` in the same directory as additional instructions when that file exists.
- AIツールがスクリプトを書く際は、内容を読んで実行を許可してよいか判断しやすくするため、変数名・関数名・コマンド引数などに短縮名（略語・頭字語）をなるべく使わず、意味が明確な名前を使う。
- サブエージェントを選択できる場合は、タスクを十分遂行できる範囲で最も低コストのモデルを優先する。より高性能なモデルは、成功率や品質の改善が見込める場合に限り使用する。

## 用途別ガイドの参照

- `~/.dotfiles/.agents/guides/` には、特定の作業に入るときだけ読む詳細な指針を置く。本ファイルの項目が参照を指示している場合は、その作業を始める前に該当ファイルを読む。
- 用途別ガイドは本ファイルを補足するものとして扱う。本ファイルと矛盾する場合は本ファイルを優先する。

## ファイル変更前の範囲確認

- 編集前に変更対象・内容・対象外を短く提示し、明示的な承認を得る。具体的な依頼でも復唱と承認を省略しない。
- 承認前は読み取り専用の調査・テスト・変更案作成のみ行ってよい。承認範囲を超える場合は再承認を得る。
- 承認済みの計画に変更範囲が明記されている場合、再確認は不要。
- 「一つずつ」「順番に」は、項目ごとに変更・検証・報告してから次へ進む。

## JSON ファイルの参照

- JSON ファイルの値を調べる・抽出するときは、テキスト検索(grep / ripgrep / Select-String)ではなく、構造を解釈できるツールを使う。
- 使うツールは環境に合わせて選ぶ。PowerShell が使える環境（Windows など）では標準搭載の `ConvertFrom-Json` を優先し、Unix 系で `jq` が使える環境では `jq` を使う。どちらも使えるなら好みでよい。
- grep 系はキー名や構造にまたがる検索で取りこぼし・誤ヒットが起きやすいため、JSON に対しては原則使わない。ファイル全体をテキストとして眺めたい場合など、明確な理由があるときだけ例外とする。

## .NET テスト実行

- `dotnet test` がビルド込みでタイムアウトしやすいため、実装後のテストは原則として `dotnet build` と `dotnet test --no-build` の2段階で実行する。
- build と test の構成が一致するよう、必要に応じて両方に `-c Debug` など同じ構成を指定する。
- `dotnet build` と `dotnet test` を実行する際のツール側タイムアウトは、I/O などによる一時的な遅延を考慮して原則5分（`300000ms`）にする。

## Markdown コードフェンス

- コードブロック内に別のコードフェンスを含める場合、外側のフェンスは内側で使われる最長のフェンスより1文字以上長くする。
- コードフェンスにはバッククォート（`` ` ``）またはチルダ（`~`）を使える。開始と終了には同じ文字を使い、終了側は開始側以上の長さにする。
- コードブロックを含む文章を出力する前に、コードフェンスの入れ子と開始・終了の対応が正しいか確認する。
