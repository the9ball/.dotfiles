# review-watch の方針の変遷

`SKILL.md` は現時点で有効な手順を書く。ここには、後から理由を独立して参照する価値がある
方針の転換だけを残す。表現の修正や軽微な追記は記録しない。

## 2026-08-24 下読みを監視セッションから別セッションへ移した

HEAD: `0cdae10cb6ef5ad57cef65120d0f15c6abb7307e`

### 変更の要約

下読みの実行主体を変えた。

- 変更前: 監視セッションが通知を受け、そのままサブエージェントへ委譲して下読みさせ、
  結論を受け取ってレポートを書いていた。委譲は差分の大小によらず必須。
- 変更後: **監視セッションは通知だけを行い、下読みは別セッションで行う。**
  下読みセッションは自分で読んでよく、サブエージェントへの委譲は規模で選ぶ。

あわせて素材の置き場と命名規則を変えた(後述)。

### 理由

委譲で守れるのは監視セッションのコンテキストだけで、**指摘の根拠は誰の手元にも残らない。**
サブエージェントから返るのは結論だけなので、「この指摘の根拠を出して」「同じパターンが
他にないか見て」と言われた時点で、誰かが差分を読み直すことになる。
実測でも、60ファイル・+3188/-34 の PR で返ってきたのは要旨1行だった。

下読みセッションを分ければ、読んだ本人がそのまま議論相手になる。読み直しが消え、
引き継ぎプロンプトを書き起こす手間もなくなる。監視セッションの軽さは、
「下読みを一切やらない」ことで以前より強く守られる。

副産物として、委譲を必須から選択に変えられた。監視セッションを守るための委譲が不要になり、
規模に応じて自分で読むかどうかを選べる。委譲を減らせば「委譲先の報告を鵜呑みにしない」
ための裏取りコストも減る。

### 検討した代替案

**下読みしたサブエージェントを `SendMessage` で再開して追加質問する。**
差分を読んだ状態が保たれているので安く済むが、答えは監視セッション経由で返るため、
議論が続くほど監視セッションが重くなる。

**採らなかった案であり、現行運用では使わない。** 監視セッションでの下読みは
往復数によらず禁止(`SKILL.md` A-4)で、ここに例外はない。
「1〜2往復なら安い」という性質自体は事実だが、それを認めると禁止の線が引けなくなる。

**監視セッションで議論を続ける。** 最も手間がないが、これが避けたかった形そのもの。
1回でも下読みを抱えると重さが以降ずっと残り、コンパクションを自分から呼べない
(`/compact` はユーザー側のコマンド)ため、いつ自動要約が走るかも選べない。

**監視セッションが引き継ぎプロンプトを生成し、ユーザーが別セッションへ貼る。**
実際に一度検討した。素材の置き場と命名規則を PR 番号から決まる形にすれば、
プロンプトを書き起こす作業そのものが要らなくなるため採らなかった。

### 影響

- 監視セッションから下読みセッションへの移行が手動になる。ユーザーが新しいセッションを開き、
  対象の PR を伝える必要がある。素材が識別子から引けるので、伝えるのは
  PR の URL(または `owner/repo#番号`)だけで足りる。
  当初この判断を「PR 番号だけで足りる」と書いていたが、番号はリポジトリごとの採番であり、
  それだけではリポジトリが決まらない。同日のレビューで指摘を受けて訂正した。
- 下読みセッションは 1 PR で使い捨てにする前提。複数 PR を1セッションで抱えると、
  監視セッションで起きていた問題が場所を変えて再発する。

## 2026-08-24 レポートのファイル名から GUID を外した

HEAD: `0cdae10cb6ef5ad57cef65120d0f15c6abb7307e`

### 変更の要約

- 変更前: `<owner>-<repo>-<PR番号>-<GUIDの先頭8文字>.html`
- 変更後: `<owner><repo>-<PR番号>.html`。差分も同じ場所に
  `<owner><repo>-<PR番号>.diff` で置く。再下読みは上書きする。
  `owner/repo` の `/` は区切りを増やさないため削除して連結する。

差分の置き場も変えた。セッション固有の scratchpad から `%TEMP%\claude-pr-review\` へ移し、
7日掃除の対象に `*.diff` を加えた。

### 理由

**owner・repo・PR 番号の組み合わせは1 PR に対して一意で、GUID を足す意味がなかった。**
GUID を付けていたのは「同じ PR を2回下読みしたときに前回のレポートを上書きしないため」
だったが、上書きされて困る場面が実際には無い。むしろ末尾がランダムなせいで、
同じ PR のレポートが複数あるときに新旧を判別できなかった。

外した効果は引き継ぎに出る。**パスが識別子(owner・repo・PR 番号)から計算できる**ため、
別セッションはグロブで探す必要がなく、PR を指定するだけで前回の素材に到達できる。

差分を scratchpad から出したのも同じ理由。scratchpad のパスにはセッション ID が入り
(`.../<session-id>/scratchpad/`)、セッションが終わると消えるため、別セッションから引き継げない。

上書き中に失敗して壊れたレポートが残る可能性は受け入れる。一時名で書いてからリネームすれば
防げるが、揮発ファイルに対しては過剰で、壊れたら作り直せばよい。
