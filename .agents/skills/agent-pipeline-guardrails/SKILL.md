# Agent Pipeline Guardrails

Architect / Implementer / Reviewer / Investigator は個人用サブエージェント(`~/.claude/agents/architect.md` /
`implementer.md` / `reviewer.md` / `investigator.md`)。オーケストレーション専用の自動化スキルは意図的に作っていない
(パイプライン全体を自動連鎖させると、途中の人間の承認ポイントが失われるため)。このスキルは自動化の
代わりに、オーケストレータ(このセッション自身)が守るべき最低限の確認ルールをまとめたもの。

## 守ること

1. **Architect への計画書き換え指示は、ユーザーの明示的な承認を得てから出す。**
   - Implementer/Reviewer/Investigator からのフィードバックを Architect に渡すときは、単に転送するだけでなく、
     フィードバック内容と(あれば)Architect が提案した修正案をユーザーに提示し、承認を得てから
     「この内容で計画を修正して」のように曖昧さのない指示を出す。
   - 「対応して」「良きに計らって」のような曖昧な依頼で済ませない。Architect 自身も「明示指示が
     無ければ書き換えない」という基準で動くよう定義されているので、オーケストレータ側が先に承認を
     飛ばしても大事故にはなりにくいが(Architect 側が提案止まりにする)、ユーザーの意図を確認せずに
     話を進めてしまうことに変わりはない。

2. **Implementer の実装を本番採用として扱う前に、ユーザーの明示判断を得る。**
   - プロダクト側の制約(AI 生成コードは本番に含められない。デバッグ用の一時コードのみ、都度の判断で
     許可される)により、Implementer の最終報告(本番/デバッグ分類・変更ファイル一覧)は必ずユーザーに
     提示し、採否を確認してから次に進む。
   - **このゲートは変更規模やモードに関係なく必ず通す。** 計画ファイル無しの直接タスクモードで1行だけ
     修正した場合でも省略しない(制約は変更の規模と無関係なため)。
   - 却下する場合は、Implementer が報告した「却下時の戻し方」(既存ファイルは `git checkout`/`restore`、
     新規ファイルは削除)に従う。

3. **迷ったら止める。**
   - 何が承認されたのか自分で不確かな場合、確認を省略せず、ユーザーに一度尋ね直す。

4. **フィードバックを鵜呑みにせず、中継前に自分で不明点を確認する。**
   - Reviewer/Implementer/Investigator からのフィードバックを別のエージェント(特に Architect)に中継する前に、内容を
     読んで自分が本当に理解できているか確認する。曖昧・矛盾している・根拠が薄いと感じた箇所を、都合よく
     解釈・要約して埋めない。
   - 不明点があれば、先に(Architect などへ中継する前に)ユーザーに確認する。ユーザーへの確認を省略して
     推測で中継すると、その推測がそのまま計画やコードに反映されてしまう。

## いつ Codex(Implementer)をデフォルトにするか

判断基準は単純な二値: **このスレッド内で、このスキル(agent-pipeline-guardrails)が一度でも読み込まれたか**。
これは「このスレッドで既に Architect/Implementer/Reviewer のいずれかを使い、計画ファイルを作成・参照
済みである」ことの目印として扱ってよい。

- **このスレッドで一度でも読み込まれていれば**: それ以降このスレッド内での実装(コード変更)作業は、
  下記「素通しゲート」に該当しない限り、自分で Edit/Write するのではなく、既定で Implementer
  経由で Codex に委譲する。「Implementerで」という明示的な指名は不要。計画がまだ無い新規タスクが
  スレッド内で出てきた場合、Architect を先に通すかどうかは下記「Architect を先に通すか」で判断する
  (規模によらず必ず計画を作る、ではない)。
- **このスレッドで一度も読み込まれていなければ**: この既定ルーティングは適用しない。Codex/Implementer
  のことは一切気にせず、これまで通り自分で直接コードを書いてよい。

### Architect を先に通すか(計画がまだ無いタスクのルーティング)

計画がまだ無いタスクを Implementer に渡すとき、**Architect を通すかどうかはタスクの規模で分岐させる**。
全タスクに計画ファイルを作らせると、1行修正のような軽微な変更でも runbook 作成が先に入って著しく
非効率になるため。判断は次の順序で行う。

1. **下記「素通しゲート」の4条件をすべて満たす** → パイプラインを通さずオーケストレータ自身が実装する。
2. **ユーザーが Implementer を指名した、または素通しゲートの条件1〜3(規模・設計判断なし・検証が
   ビルド/テストで完結)を満たすが Codex に書かせたい** → **Architect を飛ばして Implementer に直接渡す**
   (Implementer の「直接タスクモード」)。計画ファイルは作らない。呼び出し時は計画ファイルのパスを渡さず、
   変更内容そのものをタスクとして渡す。
3. **上記に当たらない** → 従来どおり Architect で計画を立て、ユーザーの承認を得てから Implementer に進む
   (この順序は省略しない)。目安: 設計判断が必要、複数レイヤー・複数ファイルにまたがる、影響範囲が
   読めない、自動生成物の再生成やスキーマ変更などの副作用を伴う。

- **迷ったら Architect 先に倒す**(ガードレール3と同じ)。ただしユーザーが「軽微だから直接やって」と
  明示している場合はその判断を尊重する。
- Implementer 側にも同じ上限が定義されている(`implementer.md` の「直接タスクモードの上限」)。直接渡した
  あとで上限超過だと判明した場合、Implementer は着手せず Architect への引き継ぎを提案して止めるので、
  その報告を受けたら Architect からやり直す。
- どの経路を通っても**実装承認ゲート(ガードレール2)は必ず通す**。軽量パスは「計画を省略する」ものであって
  「ユーザーの採否判断を省略する」ものではない。

### 素通しゲート(Architect/Implementer を通さず自分で実装してよい条件)

次の条件を**すべて**満たす場合のみ、パイプラインを通さずオーケストレータ自身が Edit/Write で実装してよい。
一つでも満たさなければ Implementer に渡す(Architect を先に通すかどうかは上記のルーティングで判断する)。

1. 変更対象が 2 ファイル以下で、追加・変更行が合計で概ね 30 行以内に収まる見込みである。
2. 設計判断を含まない。既存パターンの踏襲、明らかな誤りの修正、文言・定数・設定値の変更のいずれかに当たる。
3. 検証がビルド・テストの実行、または差分の目視確認で完結する(環境を起動して挙動を追う必要がない)。
4. ユーザーが Architect / Implementer を明示的に指名していない。指名があれば規模によらず従う。

迷う場合はパイプラインを通す側に倒す。ただし「迷ったから通す」を繰り返して小さな修正まで Architect に
流すと、計画作成(Opus)のコストが実作業より大きくなる。上の4条件を実際に当てはめて判断し、素通しした
場合は「軽微と判断し直接修正した」旨を一行で報告して、判断をユーザーが追えるようにする。

**素通ししても実装承認ゲートは省略しない。** オーケストレータ自身が書いたコードも AI 生成コードであり、
「守ること」2 の本番採用判断(本番/デバッグ分類・変更ファイル一覧の提示と採否確認)は同じように必要。
素通しで省略できるのは Architect の計画作成と Implementer への委譲だけであり、ユーザーの承認は省略できない。

## Codex に渡すモデルの指定

`implementer.md` 自体にはモデル名をハードコードしない(モデルは変更・廃止されやすく、ファイルが陳腐化する
ため)。代わりに、このスレッド内でユーザーが Codex 委譲時に使うモデルを明示的に指定したら、それを以降
このスレッド内の Implementer への委譲(`codex:codex-rescue` に渡すタスク文の `--model <name>`)に反映する。
スレッドを跨いでは持ち越さない(新しいスレッドではまた指定が無ければ既定(モデル指定なし)に戻る)。

## Reviewer を呼ぶかどうか

**大前提: `reviewer` を呼ぶのは、このスレッド内で Implementer(計画ファイルモード / 直接タスクモードの
どちらでもよい)経由でコード変更を行った場合に限る。** それ以外の変更・調査は、レビュー依頼が明示されて
いても `reviewer` を使わず、オーケストレータ(このセッション自身)が差分を読んでレビューする。

`reviewer` を使わずオーケストレータ自身がレビュー・調査する場合:

- 素通しゲートに該当してオーケストレータ自身が Edit/Write で実装した変更
- ユーザーが自分で Codex に指示して作った差分(Implementer を経由していないもの)。この場合、レビュー依頼が
  来る時点で Codex 側の作業は既に終わっており、Claude 側に戻ってきている。ここで Codex にレビューを投げ直しても
  無駄になるため、Claude 自身の判断でレビューして返す
- 既存コードの不具合・バグ報告の原因調査(`reviewer` の役割ではない。環境を起動して挙動を追う必要があるなら
  `investigator` を使う)

Implementer 経由の変更であっても、`reviewer` は Opus で走り差分と関連コードを読み直すため、小さな差分では
報告を書くコストが実作業を上回る。次のいずれかに当たるときは省略してよい(省略した旨は報告に一行残す)。

- Implementer の検証がすべて通っており、差分が 1〜2 ファイル・低リスク(設定値やログ出力の変更など、
  ロジックの分岐を増やしていないもの)である

逆に、次のときは規模が小さくても(Implementer 経由であれば)`reviewer` を呼ぶ。

- セキュリティ・認証・認可・外部入力の扱いに触れている
- Implementer が計画からの逸脱を報告している、または検証を一部スキップしている
- 本番採用を前提にした変更である(デバッグ用の一時コードではない)

ユーザーが「レビューして」と依頼したときは、Implementer 経由の変更であれば規模によらず呼ぶ。この省略基準は
オーケストレータの既定動作に対してのみ適用され、明示依頼を上書きしない。ただし**大前提は明示依頼でも
上書きされない**: Implementer を経由していない変更のレビュー依頼は、`reviewer` に渡さずオーケストレータ自身が
レビューする(ユーザーが `reviewer` を名指しした場合はその指名に従う)。

## PR 作成前の最終レビュー

「PR 前の最終レビュー」といった依頼のときも、レビューを走らせるのは Claude 側だけにする。**オーケストレータから
`codex:codex-rescue` にレビューを投げることはしない。** 実運用ではユーザーが自分で Codex に指示して作業を
終えてから Claude 側に戻ってくることが多く、その時点で Codex にレビューを投げ直しても無駄になるため。

- **Claude 側のレビュー**: 上の「Reviewer を呼ぶかどうか」の基準に従う。Implementer 経由の変更なら `reviewer` を
  `Agent`(`run_in_background: false`)で呼び、そうでなければオーケストレータ自身がレビューする。
- **Codex の第二意見が欲しい場合**: ネイティブの `/codex:review` / `/codex:adversarial-review` は
  `disable-model-invocation` のためオーケストレータからは起動できない。必要だと判断したらユーザーにその旨を伝え、
  ユーザー自身にスラッシュコマンドを実行してもらう。結果を貼ってもらえれば、Claude 側のレビューと突き合わせて
  合成する。
- **合成する場合**: 両者の指摘を突き合わせ、(a) 両方が挙げた指摘(確度高)、(b) 片方だけが挙げた指摘(出所を明示)、
  (c) 両者で判断が食い違う点、を整理して1つの総合レビューにする。安易に片方を正としない。食い違いは
  「どちらの言い分か」を残したまま提示し、最終判断はユーザーに委ねる。
- **最終レビューでも修正はしない**: これはあくまでレビュー。指摘に基づく修正は別途行い、本番採用の可否は
  ユーザーが判断する(このスキルの他のガードレールと同じ)。

## なぜ

このガードレールはプロンプトの表現(何をもって「承認」とするか)を明確化するだけであり、技術的な
強制力はない。Architect 自身も過去に「対応してください」という曖昧な依頼を書き換えの許可と誤って
解釈したことがあり(2026-07-10 のテストで発見・修正済み)、オーケストレータ側にも同じ種類のリスクが
ある。技術的に権限を制限できる箇所(コード編集ツールの有無、作業ディレクトリの範囲、既定モデルなど)は
既に各エージェント定義側の `tools`/本文ルールで対応済み。ここでカバーしているのは、それでは塞ぎきれない
「言葉の意味の解釈」に関わる部分だけ。
