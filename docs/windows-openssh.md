# Windows OpenSSHの運用記録と検証前案

## 現在の位置付け

2026-10-25時点の記録です。新規端末ではWindows標準のオプション機能を基本の選択肢とし、SSHサーバーはaqua管理外とします。
検証したWindowsホストでは、利用者判断によりZIP版10.0.0.0p2-Previewを暫定運用しています。
この結果はPreviewを安定版と扱う根拠や、他端末へ自動展開する承認ではありません。
`chezmoi apply`によるSSHサーバーの導入・更新・サービス操作、設定・ホスト鍵・認証の自動変更は追加していません。

## 復旧と保守の参照

サーバー復旧の正本は、対象ホストの保護された作業領域に保存した`RECOVERY.txt`です。
RDPはWindows未ログイン状態から接続可能であることを確認済みで、直接操作とともに非SSHの復旧経路として使います。
[標準版への切り戻し実績](https://github.com/the9ball/.dotfiles/issues/144#issuecomment-6250762039)と、[起動方式を含む復旧手順の更新](https://github.com/the9ball/.dotfiles/issues/144#issuecomment-6251322933)を参照してください。

起動設定まで戻すC1後の復旧手順全体は未実行であり、B1の切り戻し実績と区別します。
READMEのシェル設定二値のRestoreや、旧DEBUG3／`-E`へ戻すA1のログ復旧は、サーバー全体の復旧とは別です。

将来の版更新、別端末への展開、保全比較の残課題は[Issue #149](https://github.com/the9ball/.dotfiles/issues/149)で追跡します。
PATH差分のうち、書き換えた主体・時刻を確定できていない項目があります。

A1・A2のログ整理は完了していますが、Issue #149全体の完了を意味しません。
今回の文書反映のために追加検証、サービス再起動、ログ容量監視は行いません。

## 標準版維持と例外採用の条件

### 標準版を維持する場合

| 状況                                                | 判断                                                               |
| --------------------------------------------------- | ------------------------------------------------------------------ |
| PQCの必要性、保守担当、復旧手段、互換性の証拠が不足 | 標準版を維持し、移行を保留します                                   |
| Microsoft Supportが必要、またはPreviewを受容しない  | 標準版を維持します                                                 |
| 標準版でPQCの実接続が確認できる                     | 標準版で目的を達成し、Previewへ移行しません                        |
| 両方式に関連する脆弱性がある、または修正状況が不明  | 更新、公開範囲の制限、停止を比較します。旧版を安全と決めつけません |

標準版がPQC未対応なら、PQCの受け入れ条件は未達としてIssueに残します。
警告抑制はPQC対応の完了条件に含めません。
オプション機能の削除と再追加でPQC対応版になるとは保証できないため、調査目的では実行しません。

### Previewを検証用途に使う条件

- 公式取得元、版、アーキテクチャ、ZIPとMSIそれぞれのSHA-256を固定します。
- 取得した配布物の署名と同梱物を確認します。ハッシュ一致だけで発行者を証明したとは扱いません。
- 隔離VM、専用の試験鍵とアカウント、保存先、待受範囲、停止方法を定めます。
- 対象フェーズの実行承認を得ます。文書の承認やIssueへの記録は実行承認を代替しません。

### Previewを本番用途に例外採用する条件

次の条件をすべて満たす場合に限り、採用と実行の承認を別に求めます。

1. PQCを必要とする通信と理由が明確で、標準版維持の残存リスクと比較できる。
2. Windowsへの脆弱性の適用可能性、バックポート、依存ライブラリを評価し、重大な関連事項が未評価で残っていない。
3. P2のサービス試験と復旧試験、利用する全クライアントと経路の試験が合格している。
4. ssh-agentを含む変更範囲を把握し、既存の鍵、認証、ACL、既定シェルを保全できる。
5. 代替管理経路、復旧元、判断者、許容停止時間が決まり、実測した復旧時間が許容範囲内である。
6. 更新確認と脆弱性対応を継続する担当者が決まっている。
7. 対象版、端末、公開範囲、残存リスク、再評価条件を限定して、Previewの位置付けを含む例外承認を得ている。

試験に合格しても配布元のnon-production ready表記は変わりません。
唯一の管理経路がSSHの場合や、必要な接続経路が動かない場合は本番移行しません。
版、OSビルド、主要設定、公開範囲、関連脆弱性が変われば証拠の適用範囲を再評価します。

## P0からP4の実施境界

| フェーズ | 目的                   | 前提と範囲                                           | 合格が意味すること                                           |
| -------- | ---------------------- | ---------------------------------------------------- | ------------------------------------------------------------ |
| P0       | 証拠と手順の固定       | 読み取り専用。候補と変更範囲、試験票、復旧元を整理   | 実行を判断できる状態。実機動作の保証ではありません           |
| P1       | ZIPのPQC試験           | 別途承認した隔離VMで前景起動。サービスを登録しない   | 指定した環境でPQC鍵交換が成立                                |
| P2       | MSIサービス試験        | 別途承認した代表VMで導入から標準版復旧まで確認       | サービス、認証、必要機能、復旧の試験結果                     |
| P3       | 対象端末固有の並行確認 | P2で安全条件を確認後、必要時だけ別途承認             | 対象端末の指定経路での結果。サービスとの同等性は保証しません |
| P4       | 例外採用後の本番移行   | 採用承認、実行承認、停止計画、復旧実証がそろってから | 承認された構成での運用開始                                   |

P1とP2は独立した証拠です。
P1成功をP2の合格へ引き継ぎません。
P1が前景起動の権限不足で成立しなくても、PQC非対応とは断定しません。
P2を独立して実施し、サービス経由でPQCも確認した場合は、その環境の結果として記録します。

### 全フェーズ共通の中止条件

- 署名や取得元、実体パス、ハッシュ、設定の対象を確認できない。
- 意図しない待受、ファイアウォールの公開、既存22番やssh-agentへの干渉が発生する。
- 既存の鍵、ACL、認証、既定シェルに想定外の変更がある。
- 新しい権限エラー、必要機能の失敗、許容値を超える遅延が再現する。
- 代替管理経路、復旧元、承認範囲を維持できない。

該当したら新しい接続の追加と変更操作を止め、証拠を保全して対象フェーズの復旧へ進みます。
権限緩和、パスワード認証の有効化、ForceCommand、既定シェル変更で試験を通しません。
復旧に必要な操作も実行前の承認範囲へ含めます。

## P0の確認項目

対象の読み取り確認は、それ自体の許可範囲と必要権限を確認してから行います。
この文書の作成時点では、次の端末固有情報は採取していません。

1. OSビルドと更新状況、OpenSSHオプション機能の状態を確認する。
2. sshdとssh-agentの実体パス、実行アカウント、開始方式、必要権限、サービスACL、障害時処理を記録する。
3. 旧sshd_config、有効設定、Include、Match、Subsystem、ホスト鍵指紋、認証ファイルの場所とACLを確認する。
4. DefaultShell、DefaultShellCommandOption、DefaultShellEscapeArgumentsの値、型、未設定状態を記録する。
5. 対象ファイアウォール規則、PATH、ETW、IFEO緩和策の存在と値を記録する。
6. 復旧元と対象OSビルドへの適用可能性を確認し、試験票を完成させる。

サービス設定は `sc.exe qc`、`sc.exe qprivs`、`sc.exe qfailure`、`sc.exe sdshow` などの読み取り結果を区別して保存します。
PATH上のssh.exeの版をsshdサービスの版とみなしません。
HKLMのOpenSSHツリー全体にはagent関連情報があるため、シェル値の記録を目的とした無差別なエクスポートは避けます。

## P1でZIPのPQC鍵交換を確認する

### 前提と操作範囲

隔離VMのスナップショットまたは同等の復元手段を用意し、試験用鍵とアカウントだけを使います。
対象アーキテクチャのZIPを専用ディレクトリへ展開し、sshd-session.exe、sshd-auth.exe、DLLを含む配布物を一式保持します。
本番の秘密鍵をVMへ持ち込みません。

`install-sshd.ps1`、MSI、サービス登録、共有レジストリ変更は実行しません。
同スクリプトは既存のsshdとssh-agentを停止して再作成するため、並行試験の準備には使えません。[固定ソース](https://github.com/PowerShell/openssh-portable/blob/b8c08ef9da9450a94a9c5ef717d96a7bd83f3332/contrib/win32/openssh/install-sshd.ps1)

### 実施する順序

1. 試験専用ディレクトリと秘密鍵のACLを確認し、専用ホスト鍵を用意する。
2. 最小の検証用設定にループバック待受、専用ポート、専用鍵、試験ユーザー制限を明記する。
3. 候補sshdの `-t -f` で構文を確認し、`-T -f` で待受とKEXを確認する。必要なMatch条件は `-C` で確認する。
4. 別の管理端末を保持し、候補を `-D -e -f` で前景起動する。
5. 既知の試験鍵を照合した専用known_hostsを使い、PQC対応クライアントで接続する。
6. 通常交渉と試験限定のKexAlgorithms指定を別に実施して、実際の選択方式とKEX完了を記録する。

次は未実行の設定例です。
試験票に記入した専用パスと試験ユーザーへ置き換え、候補版が受け付けることを構文検査します。

```text
Port 22222
ListenAddress 127.0.0.1
HostKey C:/OpenSSH-PQC-Test/ssh_host_ed25519_key
AllowUsers pqc-test
PubkeyAuthentication yes
PasswordAuthentication no
```

認証を完了させないPQC試験には、`PreferredAuthentications=none`、`BatchMode=yes`、`StrictHostKeyChecking=yes` と専用known_hostsを指定します。
`ssh -vv` のKEX選択とNEWKEYS完了を確認し、その後の認証失敗による終了コード255をシェル試験の成功とは扱いません。
期待する方式は `mlkem768x25519-sha256` を優先し、候補が提示する `sntrup761x25519-sha512` も確認します。[PQC解説](https://www.openssh.org/pq.html)

### 合格と失敗時の対応

KEXの一覧、通常交渉の選択方式、方式指定時の結果、ホスト鍵照合をそろえてP1の合否を記録します。
認証、PTY、Git Bash、psmuxの合格には流用しません。
権限不足なら候補プロセスを止めて制約を記録し、サービス操作へ切り替えません。
終了時は候補PIDだけを確認して停止し、試験で追加した専用資源だけを戻します。

## P2でMSIのサービス運用と復旧を確認する

### 前提と操作範囲

対象に近いOSビルド、標準版、認証区分、Git Bash、psmuxを用意した代表VMを使います。
専用の試験データで標準版の基準結果を先に採取し、実行前にVMのネットワークを隔離します。
本番22番を維持する制約はVM内の旧サービスには適用せず、その停止と復旧も承認範囲に含めます。

MSIはサービスを起動し、22番への規則を追加する定義を持ちます。
別ポート設定が引き継がれるという仮定だけで、実機へMSIを導入しません。[Server定義](https://github.com/PowerShell/openssh-portable/blob/b8c08ef9da9450a94a9c5ef717d96a7bd83f3332/contrib/win32/install/server.wxs)

Server機能でもSharedコンポーネント経由でssh-agentが変更対象になります。
agentの登録、起動、停止、権限、ETW、永続的な緩和策を測定対象へ含めます。[Shared定義](https://github.com/PowerShell/openssh-portable/blob/b8c08ef9da9450a94a9c5ef717d96a7bd83f3332/contrib/win32/install/shared.wxs)

### 実施する順序

1. P0の記録と保護されたバックアップを作り、標準版の必須経路を試験する。
2. 固定したMSIのServer機能を指定して導入し、MSIログと終了状態を保存する。公式の指定は `ADDLOCAL=Server`。PATH追加を抑える `ADD_PATH=0` は候補の実MSIで確認する。
3. 再起動要求があれば記録し、許可されたVMの再起動後に差分を採取する。
4. サービス実体と待受、FW、agent、ACL、シェル値、PATH、ETW、IFEOを基準と比較する。
5. 下の試験表でサービス実行、全必須経路、サービス再起動、OS再起動後の動作を確認する。
6. 下記の復旧手順で標準版へ戻し、標準版の必須経路と変更差分を再確認する。

既存標準サービスとMSIが競合したら停止し、必要なアンインストールやオプション機能操作をVM内の手順として確定します。
本番端末で競合を解消しながら移行する運用にはしません。
別名Windowsサービスの作成も既定手順に含めません。

## P3で対象端末を並行確認する

P2の結果だけでは対象端末の固有設定を再現できない場合に限り、必要性を判断します。
コンソールまたはRDPを保持し、固定ZIPを別配置して専用ポートで前景起動します。
既存22番のサービス、認証、ホスト鍵、共有レジストリを変更しません。

- 検証用設定のPort、ListenAddress内のポート、Include、Match、Subsystemを確認し、22番へ誤ってbindしないようにします。
- 最初はループバック限定とし、遠隔クライアントには接続元を限定したFW規則と待受を別途承認します。
- 専用の試験鍵を使う場合、known_hostsの対象 `[host]:22222` の指紋を信頼できる別経路で照合します。
- 既存鍵の参照が必要なら別途その範囲を承認し、ACLを緩和しません。試験鍵での成功を本番鍵継承の成功としません。
- 共有ホームとpsmuxへ影響する利用者試験は作業保護後に行い、既存セッションをkillしません。

管理者前景起動とLocalSystemのサービス実行は、ユーザートークンや権限が異なります。
P3成功をP2のサービス認証試験の代用にしません。
失敗したら候補PIDだけを停止し、追加した専用FW規則と試験資源だけを戻して、旧22番で別接続を確認します。

## P4の本番移行と復旧

### 実施前の判定

例外採用条件、試験票、S1〜R2の必須結果、復旧元、許容停止時間、代替アクセス、実行承認をそろえます。
復旧先にも関連する脆弱性がないか確認します。
候補版が変わった場合や新しい関連脆弱性が判明した場合は、既存の合格だけで進めません。

### 切り替え順序

1. コンソールまたはRDPから対象、承認範囲、バックアップと復旧元を再確認する。
2. 既存作業を保護し、接続停止を利用者へ周知して新規作業を止める。
3. VMで確定した対象版のMSI手順だけを実施し、導入ログと差分を保存する。
4. サービス実体、必要なFW範囲、既存ホスト鍵の指紋、認証、シェル値、agentを照合する。
5. 新規の別接続でPQCと全必須経路を確認し、許容値と停止条件に照らして継続か復旧かを判断する。

更新時に既存SSH接続が維持されるとは扱いません。
Microsoftも更新時の切断と代替アクセス確保を案内しています。[公式更新手順](https://learn.microsoft.com/en-us/troubleshoot/windows-server/system-management-components/upgrade-in-box-openssh-to-latest-openssh-release)

### P2で実証してから使う復旧順序

1. 新規変更を止め、コンソールまたはRDPで失敗内容と候補のサービス実体を確認する。
2. VMで確定した順序で候補サービスを停止し、MSIの製品と版を照合してアンインストールする。
3. 標準版バイナリとオプション機能の状態を確認する。再導入が必要なら対象OSに合う確認済みの導入元を使い、必要な再起動を行う。
4. 旧sshdとssh-agentのサービス定義、開始方式、アカウント、権限、サービスACL、障害時処理を復元する。
5. 旧設定、認証ファイル、ホスト鍵、所有者とACL、シェル値の型と未設定状態を復元する。
6. FW、PATH、ETW、IFEOの差分を照合し、今回だけの変更を特定して戻す。
7. 旧サービスを開始し、実体パスと指紋を照合して別接続で標準版の必須経路を再試験する。
8. 標準機能としての認識とWindows Update管理への復帰を確認し、残差と復旧時間を記録する。

既存のSystem32配下を手動削除したり、候補バイナリで上書きしたりしません。
MSIのアンインストールだけで旧サービスが戻るとは仮定せず、サービス復元または標準機能再導入のどちらが必要かをP2で確定します。
IFEOの緩和策にはアンインストール後も残る定義があるため、存在するという理由だけで削除しません。
`windows-ssh-shell.ps1 -Action Restore` はシェル2値の復元用であり、サーバー全体の復旧には使えません。

復旧手順が失敗したら対象を停止状態または承認された限定公開に保ち、追加の変更を判断者へ引き継ぎます。
P2では失敗を記録した後でVMスナップショットへ戻せますが、それを本番復旧手順の合格にはしません。
標準機能の再認識だけでは将来の全更新の成功を保証できないため、対象ビルドと更新元の条件を記録します。

## 更新保守と標準版への復帰

### 定期確認と更新

保守担当者を指定し、週1回の公式情報確認と重大なアドバイザリ認知時の臨時確認を運用案とします。
週1回は確認漏れを抑える調整可能な運用値であり、修正期限や安全保証ではありません。
確認を継続できない間はPreview本番採用条件を満たしません。

確認先は[MSRC](https://msrc.microsoft.com/update-guide)、[Windows版リリース](https://github.com/PowerShell/Win32-OpenSSH/releases)、[OpenSSH Security](https://www.openssh.org/security.html)、[upstreamリリースノート](https://www.openssh.org/releasenotes.html)、同梱ライブラリの公式情報です。
版番号の新旧だけで未修正CVEを断定せず、Windowsへの適用可能性とバックポートを確認します。
不明なら未評価として記録します。

更新は版を固定し、修正内容の評価、VMサービス試験、復旧確認、必要な対象端末試験、実行承認、保守時間内の適用の順で行います。
wingetを使う場合も明示的な更新制御が必要です。
現在の `winget.json`、aqua管理、chezmoi hooksへOpenSSHを追加せず、一括自動更新へ組み込みません。

### 脆弱性が判明した場合

| 状況                                   | 対応                                                         |
| -------------------------------------- | ------------------------------------------------------------ |
| 公式情報で対象機能への影響を否定できる | 根拠を記録し通常の更新判断へ進みます                         |
| 影響あり、修正版あり                   | 修正評価、必須回帰、復旧確認を経て緊急変更の承認を求めます   |
| 影響あり、修正版なし                   | 公式緩和策、公開範囲の制限、代替経路、SSH停止を比較します    |
| 適用可能性やバックポートが不明         | 新規採用を保留して調査し、既存の曝露に応じた緩和を判断します |

悪用が確認され対象が曝露している場合は週次確認を待ちません。
制限や停止も実環境の変更として別途承認します。
PQCは認証前処理や依存ライブラリの脆弱性を解消する手段ではありません。

標準版でPQCを確認できた、Previewの必要性がなくなった、保守を継続できない、修正提供が許容できない、必須機能の回帰が続く場合は標準版への復帰を検討します。
復帰先にも同じ脆弱性がある場合は、単純な切り戻しを安全策にしません。
安全な復帰先がなければ接続制限や停止を判断します。

次の作業単位はP0の残る調査と試験票の記入です。

端末固有情報とVMの利用条件が未定の間は、配布物の実行へ進みません。

文書整備には新規文書1、既存文書2とaquaコメントの変更を含み、実行コードの追加は0行です。
後続の補助診断は必要性を確かめてから判断し、全体0行で完結するとは見積もりません。
補助をすべて採用する場合の暫定見積もりは、診断80〜140行、接続結果採取80〜140行、VM結果採取40〜80行、合計200〜360行、テスト120〜220行です。
クラスや汎用インターフェース、追加パッケージは想定せず、サービス変更の自動化は見積もり対象外です。
各工程で見積もりの1.5倍かつ30行を超過する場合は停止して再見積もりします。
