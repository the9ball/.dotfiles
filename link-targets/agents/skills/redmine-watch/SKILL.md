# 担当したことのある Redmine チケットの監視

一度でも自分が担当者になったチケットを監視リストへ積み、他人が加えた変更を通知する。
**通知するだけで、チケットの中身を自動で読みに行かない。** Redmine への書き込みは一切しない。

このスキル自体を編集するときは、先に `DESIGN.md`(ファイル配置と設計判断の理由)を読むこと。

## 1. 監視を張る

`Monitor` ツールで、このスキルに同梱のスクリプトを `persistent` で常駐させる。

- `command`: `bash "$HOME/.claude/skills/redmine-watch/watch-assigned-issues.sh"`
- `description`: `Redmine の担当チケットの変更 (過去に担当したものを含む)`
- `persistent`: `true`

スクリプトをインラインで書き起こさないこと。権限の分類器に弾かれるうえ、
差分検知のロジックを取りこぼすと通知が繰り返しクレジットを焼き続ける。

**この監視は専用セッションで張る。** 他の作業をしているセッションで張ると、
そのセッションが監視の所有者になり、通知の宛先がそちらへ移る。

`Monitor` が返す task ID はユーザーに伝えて記録しておく。
常駐監視は `TaskList` には出てこない(あちらは ToDo リスト用)。

### スクリプトの中身

`$HOME/tools/Redmine.Cli/redmine.exe`(`redmine-cli` スキル参照)を1時間間隔で叩き、
状態ファイル `$HOME/.claude/.redmine-watch/watched-issues.tsv` との差分だけを標準出力へ流す。
各 CLI 呼出しは既定15秒で打ち切る(`REDMINE_WATCH_CLI_TIMEOUT_SECONDS` で変更可)。
1ポーリングでやることは4つ。

1. **参照表**: `statuses list` でステータス一覧を取り、終了扱いの ID 集合を作る。
   取得できず、前回のキャッシュも無いループは、通知も差分の前進もせず次回へ持ち越す。
2. **発見**: `issues list --assigned-to me --status open` で、いま自分が担当している
   未完了チケットを監視リストへ積む。
   初回の発見が不完全な場合は初期状態を確定せず、3回連続で不完全なら1行だけ警告する。
   完全な発見へ戻るまで初回扱いを維持し、`totalCount=0` かつ `issues=[]` は正常な完了とする。
   2回目以降は、発見に失敗しても既存の監視対象の取得を続ける。
3. **取得**: 監視リストの各チケットへ `issues show <id> --include journals` を1回ずつ投げる。
4. **差分**: 前回見た journal より後に、**自分以外**が付けた変更があれば1チケット1行で通知し、
   その直後にそのチケットの状態を確定する。

終了ステータスに入った既存チケットは、他人の未通知journalがあれば変更を1回通知してから
監視リストから落とす。新しく積んだ時点で終了している `lastJournalId=-1` のチケットは、
既存か新着かを区別できないため無通知で落とす。このRedmineで終了扱いになるのは
**保留 / 却下 / 本番適用済み / 組込み済み/完了 / リリースなし / 終了** の6つ。
本番適用済みや組込み済みへの遷移自体は1回通知されるが、監視から外れた後に付いた
差し戻しコメントは拾えない。追いたい場合は Redmine 側でステータスを戻す。

### なぜローカルに監視リストが要るか

「過去に担当した」を Redmine 側へ問い合わせる手段が無い。API で引けるのは
「いま担当しているチケット」だけで、担当を外れた時点で検索結果から消える。
コメントだけ付けて担当を渡したチケットを追い続けるには、担当中に一度検知したものを
ローカルへ積んでおくしかない。

この構造上の制約が2つ残る。どちらも設計上受け入れている。

- **監視を始める前に担当を外れたチケットは拾えない。** リストは監視開始後に積まれる。
- **ポーリング間隔(1時間)より短く担当だった場合は拾えない。**

### 重複と取りこぼしの扱い

標準出力への書き込みと状態ファイルの更新を同時に確定させることはできないため、
「重複ゼロかつ取りこぼしゼロ」は原理的に保証できない。
**取りこぼしを避け、重複を限定する**方に倒してある。

そのため、次の場合に同じ変更が2回通知されることがある。いずれも異常ではない。

- 通知を出した直後にプロセスが止まった、または所有権を奪われた(再送は最大1チケットぶん)
- 監視を張り直したとき、旧プロセスが取得の途中だった

### 取得コスト

取得パスは監視リストの件数ぶんリクエストを投げる(1件1リクエスト)。担当が外れたチケットは
一覧クエリで拾えないため、まとめて取る手段が無い。各 CLI 呼出しは既定15秒で打ち切るが、
ポーリング全体の時間上限は無い。1時間間隔なら数十件までは問題にならないが、リストが数百件に
育ったら間隔を延ばすか、`watched-issues.tsv` から手で行を削る。恒久的に取得・解析に失敗する
チケットは取りこぼしを避けるためリストに残り続ける。

## 2. 検知したときの動作

**通知するだけで、チケットを自動で読みに行かない。** 通知の1行に含まれる情報
(チケット番号、件名、現在のステータス、変更者、変更内容、URL)をそのまま伝え、
中身を追うかどうかはユーザーの判断を待つ。

伝えるときはチケットの URL を `[#番号 — 件名](URL)` の Markdown リンクにして再掲する。
通知本文そのものの描画は制御できないので、クリックできる形はこちらの応答で用意する。
コードブロックに入れるとリンクにならないので入れないこと。

標準出力へ出るメッセージは次のとおり。いずれも1行が1通知で、保存失敗や起動失敗は
状態を守るためにプロセスを終了する。キャッシュ保存失敗と初回発見失敗は監視を継続する。

- `Redmine更新:` — 監視中のチケットに他人が変更を加えた。
- `Redmine担当追加:` — 自分が新しく担当者になったチケットを監視リストへ加えた。
- `Redmine監視: Redmine への問い合わせが3回連続で失敗している。API キーの失効や接続設定を確認する` —
  参照表の取得が3回連続で失敗した。取得できるキャッシュが無ければ通知と状態前進を止める。
- `Redmine監視: Redmine への問い合わせが復旧した` — 3回以上の連続失敗後に取得が成功した。
- `Redmine監視: 初回の担当チケット発見が3回連続で不完全。次回も再試行する` —
  初回発見が3回連続で不完全になった。初回確定は行わない。
- `Redmine監視: 初回の担当チケット発見が復旧した` — 不完全な初回発見から完全な発見へ戻った。
- `Redmine監視: ステータス参照表を保存できない。監視は継続する` —
  参照表の取得は成功したが、キャッシュ保存に失敗した。同じプロセス中は再通知しない。
- `Redmine監視: 接続先 URL を解決できなかった。通知の URL が不完全になる` — 起動時に1回だけ出る。
- `Redmine監視の起動に失敗: 状態ディレクトリを作成できない (<path>)` — 終了コード1で停止する。
- `Redmine監視の起動に失敗: CLI のディレクトリが見つからない (<path>)` — 終了コード1で停止する。
- `Redmine監視の起動に失敗: 所有トークンを書き込めない (<path>)` — 終了コード1で停止する。
- `Redmine監視を停止: 監視リストの状態を保存できない` — 状態を確定できないため終了コード1で停止する。

通知に載せるのは差し戻しの検知に足りる分だけで、属性変更は名前まで解決していない
(ステータスだけは例外で、`新規→割振済` のように前後の名前を出す)。
「担当者変更」「優先度変更」の中身を知りたいときは、通知後に詳細を取る。
件名・変更者名・ステータス名に改行やタブが含まれても、通知の完成文字列を1行へ正規化する。

```powershell
redmine issues show <番号> --include journals --json
```

このコマンドの実行は `redmine-cli` スキルの方針に従い、安価なモデルの読み取り専用
サブエージェントへ委譲する。生の JSON をこのセッションのコンテキストへ残さない。
**監視セッションの本業は待機して通知を出すことで、1通知あたりを軽く保つのが価値になる。**

## 3. 停止・張り直し

**セッションや Claude Code が終了しても、スクリプトのプロセスは残る。**
ハーネス側の Monitor タスクだけが消え、プロセスはポーリングを続ける。
`TaskStop` も同じで、ハーネスの記録を止めるだけでプロセスを終わらせる保証はない。

そのため張り直しは**同じ手順をそのまま再実行してよい。** スクリプトが起動時に
`$HOME/.claude/.redmine-watch/owner-token` へ自分のトークンを書いて所有権を主張し、
先に動いていたプロセスは所有権を確認した時点で自分から退く。後から起動した方が勝つ。
起動側で残存プロセスを探したり `kill` したりする必要はない。

プロセスを確実に全部止めたいときは、このファイルへどのプロセスのものでもない値を書く。

```bash
echo stop > ~/.claude/.redmine-watch/owner-token
```

### 監視リストを操作する

**先にプロセスを止めてから触ること。** 稼働中に `watched-issues.tsv` を消すと、
次のポーリングで担当中のチケット**全件**に「担当追加」通知が飛ぶ。1行1通知なので
担当が多いほどクレジットを焼く。初回起動の無通知は、状態ファイルが存在しない状態で
プロセスが起動したときにだけ働く。

リストをまっさらにして張り直す手順:

```bash
echo stop > ~/.claude/.redmine-watch/owner-token
rm ~/.claude/.redmine-watch/watched-issues.tsv
```

このあと監視を張り直すと、初回起動として担当中のチケットが無通知で登録し直される。

特定のチケットだけ監視から外したいときは、プロセスを止めてから該当行を削る。
ただし担当中である限り、次のポーリングの発見パスで積み直され、そのとき
「担当追加」通知が1回出る。

## 4. 状態ディレクトリ

`$HOME/.claude/.redmine-watch/` に4つ置く。いずれもマシン固有で、dotfiles では追跡しない。

| ファイル | 役割 | 消したら |
|---|---|---|
| `watched-issues.tsv` | 監視リスト本体 | 過去に担当したチケットの記憶が失われる |
| `status-reference.json` | ステータス一覧のキャッシュ | 次の取得成功まで監視が止まる。保存失敗は1行だけ警告して監視を続ける |
| `self-user-id` | 自分のユーザー ID | 担当中のチケットが0件などで復元できない間は、自分の変更も通知対象になりうる |
| `owner-token` | 稼働中プロセスの所有権 | 全プロセスが退く |

## 5. やらないこと

- **Redmine への書き込み。** CLI は読み取り専用で、コメント投稿もステータス変更もできない。
  変更が要るなら人が Redmine 上で行う。
- **通知を受けて自動でチケットを調べに行くこと。** 監視対象が増えるほどコストが跳ね上がる。
  実際に読むチケットはユーザーが選ぶ。
- **API キーをプロンプト・ログ・最終回答に含めること。** 接続設定は CLI 側のローカル設定
  ファイルと環境変数だけで完結させる。
