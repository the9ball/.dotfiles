# Codex orchestration

The Decision Maker (the user) works with the Coordinator (Claude Code) and Workers (Codex CLI), optionally through the Orchestrator (ChatGPT). Under `execution-lifecycle-gate`, the Coordinator acts as coordinator and the Worker as Implementer. Advisor stays Advisor.

## Discovery contract

- Host fallback: exempt; Claude Code host instructions route a Coordinator appointment directly to this Skill
- Positive trigger: A valid explicit Coordinator appointment, user approval of a gate-flow plan naming Codex as implementer, or an explicit one-shot instruction meeting the conditions under Appointment and authority, including all required inputs.
- Negative trigger: Ordinary delegation, a single review, a task without an appointment, or execution by a host other than Claude Code.
- Conditional dependency: Apply `link-targets/agents/skills/execution-lifecycle-gate/SKILL.md` for the execution contract and gates, `link-targets/agents/skills/delegation/SKILL.md` for handoff, model selection and verification of results, and `link-targets/agents/skills/codex-invocation/SKILL.md` for CLI dispatch, resume and result handling. For external operations, apply `link-targets/agents/skills/external-operation-authorization/SKILL.md`, including the repository standing push approval when applicable. For GitHub writes, also apply `link-targets/agents/skills/github/SKILL.md` and `link-targets/agents/skills/external-posting/SKILL.md`.
- Failure mode: If the appointment, target, or authority is missing or ambiguous, stop and ask the Decision Maker. Never widen the scope. If a required dependency cannot be resolved or its installed version lacks the needed operation, stop and report the blocker. This includes a missing implementation or resume form in `codex-invocation`.

## Runtime contract

Use this Guide for the duration of a valid appointment. At task start the Decision Maker chooses the configuration. In three-layer operation, the Orchestrator handles requirements and final checks, the Coordinator coordinates execution, and Workers implement and verify. The user may also work directly with Claude Code as Coordinator and Codex Workers without a ChatGPT Orchestrator. Existing two-layer operation uses the Orchestrator and user-driven Codex.

## Guide

### Appointment and authority

- An explicit Coordinator appointment remains valid. User approval in the gate flow of a plan naming Codex as implementer also appoints Claude Code as Coordinator for that task only, subject to the required inputs below; an unapproved plan does not establish this form of appointment.
- An explicit user one-shot delegation instruction for an identified task also appoints Claude Code as Coordinator for Codex Workers for that task only when the instruction names Codex or the task's plan names Codex as the default implementer, and the plan records every required appointment input. If the instruction names another implementer, use that implementer instead and no Codex appointment arises under this form; a plan alone or user silence cannot establish it.
- This one-shot form grants no worktree-creation permission; record that limit in the plan. External operations are limited to those named in the instruction, must be recorded accordingly in the plan, and still require matching external-operation authorization. Worker and spot-reviewer model/effort come from the plan; the user's later overrides remain effective.
- A valid explicit one-shot Codex appointment also permits interim implementation by the Coordinator when Codex Workers cannot run before or during implementation because of usage limits, exhausted credits, or unavailability, under the Worker-limit rules below. This permits no other implementer, worktree creation, or unnamed external operation; stop before PR creation or any other completion-state operation, with interim commits marked as awaiting Worker review.
- Confirm the repository, Issue/PR/task, permitted external operations or none, worktree-creation permission, and the main Worker and spot-reviewer model/effort declarations. For plan-approval or one-shot appointment, take these from the task's plan (approved for the former); if any is missing, no appointment exists. Model/effort fields may be expressly unspecified, then resolve them under `delegation` by inheritance or runtime default. Preserve explicit selections.
- Worktree permission must cover the proposed creation; approval of a plan expressly specifying that creation suffices. A generic plan approval or one-shot instruction does not supply worktree permission. Recording external operations in a plan does not authorize them; match each operation against the separate external-operation contract.
- The user may override the implementer or reviewer at any time. An executor change follows the handover and reconciliation rules below before another executor writes; reviewer changes preserve mandatory review and independence requirements.
- The appointment authorizes delegation to Codex CLI Workers for the identified task and the read-only spot reviews those Workers dispatch without per-delegation confirmation. Claude Code subagents remain subject to the normal delegation rule in `CLAUDE.md`. Apply the existing scope, execution, review, Git, and external-operation contracts. PR creation, updates, and comments use the existing external authorization rules. Merge, Issue closure, permission relaxation, and new contracts require separate authorization.
- The appointment ends when the task is complete, the Decision Maker stops it, the scope changes materially, or the task is transferred to two-layer operation. Do not assume that a running session learns of an end immediately. Unrelated work requires its own authority.

### Roles and worktree isolation

- As Coordinator, fix the execution contract and target identity, manage the gates, and own commits, pushes, PRs, and GitHub records within the applicable authority.
- The main Worker changes and verifies files within the fixed contract, with Git writes and external operations forbidden. It dispatches a read-only spot-review subagent using the settings resolved under Appointment and authority. The child does not run a second lifecycle. Any Coordinator review required by `execution-lifecycle-gate` remains in force.
- Follow the kernel's worktree policy: prefer the existing checkout and avoid worktrees by default. For changes relaxing approval rules in link-published instructions, propose a worktree with reasons in the plan; create one only with explicit approval, including approval of a plan specifying its creation. Other edits to published instructions need no isolation proposal and may use the main checkout, accepting immediate visibility to running sessions.
- Before committing in a linked worktree, check `git var GIT_AUTHOR_IDENT`. If that check fails, use the identity already resolved by the main checkout of the same repository for that commit only, and record the fallback (Issue #200). Do not write it to Git configuration. If the identity cannot be confirmed, stop before committing.

### Worker request and sessions

- In the handoff, fix the repository, task, checkout and branch, permitted files, approvals, prohibited operations (including all Git writes and network access), and stop conditions. Specify the verification commands and require each command's exact exit code. Require original line endings to be preserved and new files to follow repository conventions. Specify explicit `.\` prefixes for relative script paths in PowerShell. Follow `codex-invocation` for Windows-specific request requirements.
- Include the spot review scope and the selected model and effort. Require a report of changed files, verification commands with exit codes and key results, spot findings and their disposition, and any blockers or unverified work.
- Bundle planning, implementation, verification, and spot review into one Worker call. Resume the saved session for small follow-ups on the same work, and start a fresh session for independent review. Read-only work may run in parallel. Workers may write in parallel in the same worktree when assigned file ownership does not overlap, including generated outputs; otherwise serialize the writes. Separate worktrees still require creation approval.

### Acceptance and SHA-bound review

- Inspect the actual diff for scope and line endings and run the repository's required checks yourself before push. For the9ball/.dotfiles, follow its AGENTS.md and run `pwsh -NoProfile -File scripts/check-ci.ps1` at the repository root. A Worker report does not establish acceptance.
- Worker and spot reviews are inputs to the Coordinator's gate, not the gate itself. The gate passes only when the completion conditions of `execution-lifecycle-gate` hold for the current SHA, including required verification, any selected user review, and, when Advisor review is `REQUIRED` (for example for changes to Skills, `AGENTS.md`, or agent definitions that affect approval or delegation), its final assessment. No review result replaces the Coordinator's acceptance, the Decision Maker's production-adoption decision under `agent-pipeline-guardrails`, or the separate authorization to merge.
- A PR may be created ready directly when the gate has passed for its actual head and the body records that passing result with the full SHA. Otherwise open it as Draft and record the passing result with the full SHA before marking it ready. Both routes require separate external-operation authorization; neither bypasses a gate stop or authorizes auto-merge.
- A different PR head invalidates the pass. Before pushing a new head to a PR that is ready for review, return it to Draft under the applicable GitHub authorization and keep it there until the new head passes. If returning it to Draft is unauthorized, stop before pushing and ask for authorization. If a ready PR already has a head different from the reviewed SHA, return it to Draft when authorized or ask for authorization. Any interim commits made by the Coordinator need a Worker review before completion, subject only to the returning user's explicit omission decision under the one-shot Worker-limit rules below.

### Checkpoints and recovery

- At each milestone, record the branch, full head SHA, and next step in the Issue or PR when authorized, using GitHub-safe information and the existing posting rules. If Issue or PR records are unauthorized, use another authorized place named in the appointment. If none is named, report each checkpoint to the Decision Maker at the milestone. Keep session IDs and process details local.
- **Resume only on instruction.** After any interruption of the Coordinator's session (for example a usage limit, a crash, or a restart), do not resume the task on your own. Resume only when the Decision Maker explicitly instructs it for this task. Then, before any other action, compare the last checkpoint with the current branch, local and remote head, working tree, and running Workers; stop and ask the Decision Maker if you find a change you did not make or cannot establish the current state.
- **Worker limit exhausted or unavailable.** Record an interrupted call as incomplete with its reset time (or record that the time is unknown). Keep the same account, Codex home, and route. Before retry or interim implementation, confirm that the interrupted Worker and every child or process it started have ended; if none started, record that fact. Resume a saved session only when the retry rule in `codex-invocation` allows it, or, if the appointment allows interim work, implement in Claude Code under the SHA-bound gate. Mark interim commits as awaiting Worker review; keep any existing PR in Draft under the applicable authorization. Under a valid explicit one-shot appointment, complete verification, Advisor review, commits, and authorized working-branch push only after all other normal PASS conditions hold, then hold before PR creation or any other completion-state operation. Before completion, obtain a fresh Worker review fixed to the new head SHA, never the interrupted implementation session; alternatively, the returning user may explicitly decide to omit it in the one-shot case. Neither pending review nor interim implementation itself permits completion.
- **Claude limit exhausted or Claude unavailable.** By default, wait for Claude to recover; Claude then resumes only on the Decision Maker's explicit instruction. Changes made after the last checkpoint may remain, and processes Claude started may keep writing.
- **Handover after an end.** Before any other executor works on the task's branch or PR after the appointment ends for any reason (for example, a transfer to two-layer operation or a new handoff after a material scope change):
  1. Confirm that every Claude Code session for the task, and every Worker, child, or pending process it started that could write, has ended. A running session may not have learned of the end, so confirm that it has stopped rather than assuming it.
  2. Confirm that every external write those sessions sent has a confirmed outcome under `external-operation-authorization` (an ambiguous outcome is read back before the handover continues).
  3. Reconcile the checkout's branch, full HEAD SHA, and staged, unstaged, and untracked changes against the last checkpoint, and leave to the Decision Maker how any difference is carried over.
  4. The next executor then starts from the reconciled state.

  If (1), (2), or (3) is not completed, the next executor does not start, the ended appointment stays ended, and the Decision Maker decides.
- **Transfer to two-layer operation** happens only when the Decision Maker decides it is needed, and follows the handover steps above; the task then continues in ordinary two-layer operation. Claude does not return to a transferred task; a new appointment applies only to a different task.

### Reporting and evaluation

- When authorized, record detailed discussion, decision grounds, and verification results in the Issue or PR under the existing posting rules. Report to the Decision Maker for milestone checkpoints when required above, when a decision or approval is needed, when a blocker arises, or when a PR is ready for acceptance.
- After five appointed tasks or one month from adoption, whichever comes first, evaluate the mode. For each task record human interventions (count and time), Claude and Codex usage, two-layer fallbacks and their reasons, and problems found during acceptance or review.
