# Execution Lifecycle Gate

## Purpose

Run the standard flow from planning through the completion state fixed for the task, which need not be a PR. Preserve separate scope, production-adoption, Git, and external-operation authorization. A plan is optional for execution whose goal, scope, constraints, verification, and completion conditions are already fixed; multiple files or design changes alone do not require a plan.

## Standard flow

### Planning (`PLANNING`)

1. Receive the problem and request to create a plan.
2. Clarify premise decisions while inspecting relevant material; fix the completion state and whether repository changes are needed before drafting dependent steps.
3. Create a plan with operational verification procedures and write it to a file before review. `link-targets/agents/skills/implementation-planning/SKILL.md` owns plan contents, premise decisions, estimates, and plan history.
4. Review the plan independently with Advisor and Codex at the strength defined below and reconcile their findings. The request to create a plan includes this initial review; it does not depend on later plan approval.
5. Obtain user plan approval. It authorizes the flow's subsequent slice, detailed, and correction reviews. If only a plan was requested, end here without implementation.

Plan approval establishes a Codex Worker appointment only when all conditions of `codex-orchestration` are met; it does not expand that contract's delegation authority. One-shot delegation below is a separate explicit execution instruction.

### With repository changes

6. Implement and run the planned builds/tests. Codex Workers follow `codex-orchestration`; the appointed Coordinator owns Git operations.
7. Run slice review using Advisor `iterative-confirmation` and correct findings.
8. Run the plan's operational verification, preferring autonomous Claude operations within their authorized scope; correct gaps with fixups.
9. Organize commits with lifecycle-owned autosquash, then fix the detailed-review candidate.
10. Obtain detailed review: Advisor final assessment and independent Codex review, reconciling both sets of findings. For corrections, verify, autosquash, and re-review until converged, subject to the stop rules.
11. If `effective_user_review=REQUIRED`, present the final reviewed candidate. A rejection changing scope or design returns to planning and approval; otherwise correct, verify, autosquash, and return to detailed review before presenting it again.
12. Achieve the agreed completion state only after the gate passes and each operation is authorized. `link-targets/agents/skills/external-operation-authorization/SKILL.md` owns external authorization; plan approval alone does not supply it.

### Without repository changes

6. Execute the investigation, verification, or operation. Effects on shared environments or external systems require separate authorization covering target, scale, time window, and abort conditions before execution.
7. Verify and record results.
8. Review results at the same risk-based strength as the plan review and reconcile findings.
9. Conduct the selected user review. Rejection returns to execution or result review; a scope change returns to planning and approval.
10. Record and achieve the agreed completion state, such as a report. If re-verification discovers a defect, report it to complete this task; fixing it requires a separate plan.

Commit, slice, autosquash, and commit-map requirements do not apply to this branch; use fixed result identities, result-review evidence, and completion-state records instead. The repository ledger/epoch/commit-range machinery applies only from `INPUT_FIXED` onward when repository changes are involved.

## Review contract

- `user_review` and `review_level` can be specified independently for each plan or goal run. The former controls whether normal user reviews are required, and the latter controls whether AI reviews by Advisor are required. Planned validations, existing approval/authorization gates, and other high-level rules are not omitted with any value.
- Each source is resolved separately, in this order of precedence: the explicit user or goal contract, then the corresponding specification in the plan, then the default value. There is no need to repeatedly write review procedures and trigger statements in your plan. The successor run after `PASS` will not automatically inherit the review contract and will resolve it newly.
- Plan and result reviews default to independent Advisor and Codex reviews. Only a low-risk, read-only plan with all mandatory triggers false may declare lighter reviews, finalized by user approval; mandatory-trigger plans cannot be lightened. One-shot delegation never lightens review. Record the selected strength and reasons without changing the existing `review_level` values.
- The value of `user_review` shall be one of the following.
  - `REQUIRED`: Always conduct a regular user review linked to the final candidate target. Record the snapshot identity, the content presented, the user's explicit approval or confirmation that no changes were requested, or confirmation that each item of feedback was resolved.
  - `NONE`: Record the reason, basis, and designation source for `SKIPPED` without conducting regular user reviews. If an existing higher-level rule requires a user regular review of the same candidate target, this specification alone will not invalidate it, but will stop it as a conflict and ask for confirmation. Other types of approval gates, such as editing approval, implementation acceptance/rejection, history rewriting, push, and external transmission, are handled independently of regular user review.
  - `AUTO`: Default value. Resolve to `REQUIRED` in the standard flow and `NONE` under explicit one-shot delegation; preserve applicable explicit user and higher-level requirements. Stop on unresolved conflicts.
- The value of `review_level` shall be one of the following.
  - `NONE`: Do not run Advisor. Valid only if all required Advisor triggers are false with a rationale and there is no review requirement specified in the plan, goal, or higher-level rule.
  - `ADVISOR`: Normally obtain independent review of the first fixed final candidate and a current-target final assessment under the Advisor evidence contract below. A first-review exception is valid only under that contract's explicit exception requirements.
  - `AUTO`: Default value. Choose `ADVISOR` for normal implementation gates. If there is a required Advisor trigger, apply `ADVISOR` as a lower bound.
- If `NONE` conflicts with a required Advisor trigger, do not silently honor the selected value; raise it to `effective_review_level=ADVISOR`. If the user rejects the required lower limit, stop and ask for confirmation, and do not make it `PASS` without review.
- When preflight and final candidate are fixed, record the input source, required lower limit, selection reason, and reason for execution or `SKIPPED` for `requested_user_review`, `effective_user_review`, `requested_review_level`, `effective_review_level` in the ledger. `NONE` only means omitting the selected review process, and does not mean exempting the entire quality check.
- Codex findings use the same blocking `指摘成立` / `指摘撤回` dispositions and correction evidence as Advisor findings. Codex review does not replace the Advisor's final `assessment_mode`. If Codex is unavailable, ask the user to choose whether to wait, override the implementer/reviewer, or omit it; omission is allowed only by that decision or an approved lighter review. During one-shot delegation apply the unavailable-Codex stop below.

## Runtime decision boundaries

| Situation | User available | One-shot delegation |
| --- | --- | --- |
| In-scope runtime design choice outside mandatory triggers 1–5 | Proceed with the recommendation and report | Same |
| Newly arising trigger 1–5 decision, risk acceptance, or missing evidence | Stop and confirm at the decision checkpoint | Stop the affected part at that decision; finish independent work and report; no gate PASS |
| Estimate excess, reason (a) lax estimate or (b) greater complexity | Stop and confirm | Proceed within scope and report |
| Estimate excess, reason (c) unplanned element, or scope expansion | Stop and confirm | Stop the affected part |
| Advisor `REQUIRES_USER_DECISION` | Stop and confirm | Stop the affected part at that decision; Coordinator cannot override Advisor |
| Starting an Implementer | Only the implementer designated in a user-approved plan or explicit appointment | Default Codex or its narrow interim Coordinator fallback under the explicit one-shot appointment in `codex-orchestration`, or the implementer named in the instruction |
| Lighter reviews | Declare in the plan and obtain user approval | Do not lighten |

These boundaries govern execution-time choices, not unresolved planning premises. Keep mandatory decision checkpoints; unresolved decisions/evidence never become PASS merely because independent work can continue.

## One-shot delegation

- An explicit instruction such as `そのまま実行して` ("just run it") or `PR作成まで進めて` ("proceed through PR creation") delegates this task through its stated completion state once. It does not carry to the next task or enlarge the stated completion state.
- Skip user plan approval and post-implementation user review; record `effective_user_review=NONE`, `SKIPPED`, and the one-shot instruction as its source. This is explicit prior delegation, not approval inferred from silence, and creates neither `USER_AUTHORIZED` nor `PASS_WITH_USER_AUTHORIZATION`. Resolve any conflicting higher-level review/approval obligation before proceeding.
- Adopt recommended premise decisions as `委任` (delegated), recording them in the plan and final report. Keep the plan file, AI reviews, verification, and all other gates.
- In addition to existing local authority, the instruction permits Git-recoverable edits to tracked files, in-scope new files, commits, fixups, autosquash, branch creation, plan/artifact creation in `.local/`, planned local builds/tests/linters, and flow-defined AI reviews, subject to role ownership and higher-level constraints. History rewrites require every condition of the kernel's unpublished-task-commit exception.
- It permits working-branch push only within existing standing push authorization and after gate PASS; external operations are limited to those named in the instruction and still use external-operation authorization. A completion-state label or plan listing is not authorization for unnamed operations.
- It does not authorize worktree creation, UI capabilities (including read-only UI), changes outside the project or to pre-session unmanaged files, pre-approval of planned environment operations, or delegation expansion beyond a valid Codex appointment. Existing explicit authority for an excluded operation remains independently usable.
- If work would commit on the default branch of a link-published checkout, stop before the first commit and report: routine authority does not cover switching branches there, the unpublished-task-commit rewrite exception is unavailable, and standing push authorization excludes the default branch.
- Apply stops in priority order: first, stop before any newly arising unresolved decision, risk acceptance, missing evidence, or `REQUIRES_USER_DECISION`; complete only independent unaffected work and do not pass the gate.
- Second, if a repository-change plan's scope itself meets a mandatory trigger, proceed through gate PASS, commit, and authorized working-branch push only when all intervening checkpoints are resolved and normal PASS conditions hold; stop before PR creation or the agreed completion-state operation. This never overrides the first stop.
- Third, if Codex cannot run, apply `codex-orchestration`'s one-shot interim Coordinator implementation and Worker-review rules; complete authorized implementation, verification, Advisor review, commits, and working-branch push after all other normal PASS conditions hold, but stop before the completion-state operation. This narrow pending-Codex continuation permits push, not task completion or a claim of completed/waived Codex review; established findings and unresolved decisions still block PASS. On return, the user decides whether to wait for Codex or omit it.
- Without repository changes, stop before execution if any mandatory trigger applies or an operation affects shared environments or external systems.
- With or without repository changes, if required authority is absent, an operation lies outside the permitted set, or repeated failures prevent progress, stop that part, finish independent work, and report.
- PRs remain subject to the current `codex-orchestration` Draft/ready contract and separate external authorization. Include the full gate-PASS SHA in the PR body. Set auto-merge only when named in the instruction; that instruction is the advance production-adoption decision for that operation. Otherwise production adoption remains the user's merge decision.
- Lead the final report with delegated decisions, `SKIPPED` items, stopped parts, and areas that may require rework.

## Execution contract

- Execution inputs can come from an approved implementation plan, a user's explicit change request, or a goal/implementation scope established during a conversation. Separate the presence or absence of a plan and the scale of change, and allow multiple file changes and design changes even in planless.
- Before starting implementation, fix at least `goal`, `scope`, constraints, completion conditions, approval status, target identity, `user_review`, `review_level`, verification method, and presence or absence of external operations as an execution contract. If these cannot be uniquely determined from the plan or goal, stop, and do not implicitly generate a plan to compensate for the shortage.
- The execution ledger records the contract identity, input source and hash/commit, target/exclude manifest, base/target, epoch identity, review contract, verification results, spot/slice manifest, commit range, fixup/amend/autosquash. Conflicting inputs, changes in target identity, and out-of-scope requirements will stop the gate.
- `execution_status` distinguishes at least `PLANNING`, `INPUT_FIXED`, `EXECUTING`, `REVIEWING`, `USER_CHECKPOINT`, `FINALIZING`, `COMPLETED`, `BLOCKED`. Do not represent the execution state and Advisor findings/gate state with the same value.

## Activation conditions

- Activate on a request to create or update an implementation/operation plan, a confirmed execution input or goal review contract selecting this skill, or explicit selection of this skill.
- Targets include investigation, operational verification and load-test plans, and changes to code, tests, execution/build/deployment settings, schema/data migration, generators/products, APIs/communications, or files controlling agent/tool behavior.
- Plan-only requests stop at plan approval. Explanatory-document-only edits that do not change norms, specifications, contracts, behavior, or operational procedures remain excluded. Determine the role of a change rather than its extension; normative agent/tool instructions are implementation targets.
- Describing the procedure for invoking the individual review method in the plan every time is neither an activation nor a completion condition. The application and execution order of this skill should be a common route, and the plan should only include specific review points or additional verification when necessary.
- If it is not possible to determine whether the application is applicable, please check with the user instead of treating it as exempt.

## Privileges and roles

- Do not undermine existing gates of planning, scope, implementation approval, and external operations. Review results are not approval for implementation, production adoption, or external transmission.
- The authorization boundary for external operations is a separate contract handled by `link-targets/agents/skills/external-operation-authorization/SKILL.md` and does not replace target/epoch evidence, `USER_AUTHORIZED`, `PASS_WITH_USER_AUTHORIZATION`, or fail-closed judgment.
- This reference does not change the determination of existing review contracts, identity lifecycles, ledgers, or general review requirements.
- The coordinator manages the execution contract, target identity, review epoch, commit scope, spot/slice manifest, gate state, and is responsible for semantic commit, fixup, amend, and autosquash. Advisor checks a fixed target and ledger as read-only and returns only findings and verdicts.
- The Implementer is responsible only for changes and verification within the scope of the finalized contract, and does not commit, fixup, amend, rebase, autosquash, or push. Advisor performs read-only reviews and is not responsible for Git operations or acceptance/rejection decisions.
- A normal user review of `effective_user_review=REQUIRED` is the process of presenting candidate differences and planned verification results to the user, and recording in the ledger a response that includes the user's explicit review completion/approval (including no changes) or confirmation of resolution of each feedback associated with the presented snapshot identity, and that there is no unresolved feedback. No response, plan approval alone, or ambiguous or unrelated responses that are not tied to a snapshot are not evidence of review completion. If `effective_user_review=NONE`, record this step as `SKIPPED`. Regular reviews are not a substitute for Advisor reviews.
- Advisors are not general quality reviewers; they advise on decisions such as design, security, compatibility, data integrity, disruptive migrations, and significant plan deviations. Don't silently substitute another model if an Advisor is unavailable.

### Determining whether Advisor is necessary

- The necessity of Advisor is first determined as one of `REQUIRED`, `NOT_REQUIRED`, or `UNRESOLVED`, independent of the execution result. The coordinator records the true/false/unknown status of each trigger, the applicable plan clause, path, difference range, judgment reason, evidence, and judgment entity in the ledger.
- If any of the following applies, it shall be `REQUIRED`.
  1. Add or change security, privacy, authentication/authorization, cryptography, secrets, payment, authority, or trust boundaries.
  2. Change data loss/irreversible operations, destructive migrations, persistent data integrity, or rollback capabilities.
  3. Affects distributed consistency, concurrency, ordering, idempotency, and correctness of multiple services/multiple version deployment.
  4. Breaks public APIs, communication formats, storage formats, schemas, compatibility guarantees, or requires staged deployment.
  5. Requires design decisions that are not in the approved plan or execution contract, and at least one choice changes one of the above risks, component boundaries, persistence method, compatibility, or rollback policy.
  6. Change control rules such as `AGENTS.md`, `SKILL.md`, agent definition, authority/sandbox/routing/tool/plugin settings, and affect activation, approval, write/external transmission, destructive operations, delegation/model/tool selection, target identity/evidence, role independence, suspension, `USER_AUTHORIZED`, or `PASS`.
  7. There are significant deviations from the approved plan or execution contract that require a risk acceptance decision, multiple significant potential causes remain, or evidence-based fixes to the same problem fail twice.
  8. Operations impose load or irreversible effects on shared environments or external systems, including load tests.
- A change to `AGENTS.md` or `SKILL.md` alone does not make Advisor review `REQUIRED`. For typos, formatting, link corrections, or paraphrasing that does not change meaning, the initial Advisor requirement may be set to `NOT_REQUIRED` only if the basis for normative equivalence can be recorded. This does not extend the `REVIEW_PRESERVING` allowlist for inheriting existing evidence into a successor revision; that follows the rules in `Revision and review-preserving classification`.
- The necessity is determined in the following order: `REQUIRED` if any trigger is true, `UNRESOLVED` if there is no true and even one unknown, and `NOT_REQUIRED` if all are false. If true and unknown are mixed, `REQUIRED` takes precedence.
- In the case of `UNRESOLVED`, run the Advisor or report the stop/confirmation to the user, record additional evidence in the ledger, and redo the three-value judgment. Advisor's answer `CLEAR` does not automatically change the necessity to `NOT_REQUIRED`, and stops if unknown remains. `UNRESOLVED` must not be recorded as `NOT_REQUIRED` without verification.

### When to run Advisor and add checkpoints

- A request to dispatch an Advisor resolves the loaded Skill's symlink/junction to an entity path and follows the `link-targets/agents/skills/advisor-review/SKILL.md` read scope contract based on the instruction root resolved for this loaded Skill entrypoint by the strict real-path procedure recorded in `link-targets/agents/guides/README.md` (Reference path); stop if it cannot be resolved. The instruction root is only for reference in the shared guide, and the work root, target identity, and comparison criteria are fixed separately. Fix the path, target identity, epoch identity, mode, primary scope, surrounding context, excluded scope, and dependency closure of each target file to the request statement and ledger, and specify the line range starting from 1 and including both ends and stable anchor for partial references. Record the actual reading range, additional range, and unconfirmed range in the Advisor response, and if the required range or dependent closure remains unconfirmed, it will not be treated as `CLEAR`.
- In preflight, determine necessity by three values. Spot and slice Advisor after implementation and planned builds/tests, before operational verification, use `iterative-confirmation`, preferring parent inheritance where supported. Fix their manifests and complete corrections and dependency-boundary checks; a spot is not full-change coverage and neither spot nor slice substitutes for the final assessment. For `NONE`, retain coverage and record Advisor as `SKIPPED`. After slice convergence, operational verification and autosquash, fix the first final candidate and normally dispatch one fresh `independent-review` for the full change and its dependency boundaries, before selected user review. Any exception requires an explicit applicable contract, not a cost or size heuristic. Subsequent milestones use the Advisor evidence contract below rather than mechanically dispatching another independent reviewer. `REQUIRED` still requires sufficient Advisor evidence and a current-target final assessment; `UNRESOLVED` still requires evidence-based reclassification. `NOT_REQUIRED` can omit Advisor only if every trigger is false with evidence in the final target and `effective_review_level=NONE`.
- If there is an important decision point before or during implementation that cannot be safely continued if you wait until the final stage (security/trust boundaries, irreversible data changes/migration, public API/compatibility, distributed consistency/rollout, or significant unplanned design/risk acceptance), be sure to dispatch an additional checkpoint in Advisor before passing/confirming/committing/implementing the decision, and stop the decision point and the continuation of work until the result is `CLEAR`. Stop and report to the user even if it is not executable, `BLOCKED`, `REQUIRES_USER_DECISION`, or any other non-`CLEAR` result. Each checkpoint records the decision purpose, specific question, target scope/epoch, reason, result, and next decision in the ledger, and does not substitute for the final Advisor decision.
- Additional checkpoints can be added at most twice per allowance, including all intervening epochs due to fixup/amend; resets follow the counter-reset rule in Stop/confirm conditions. If you need a third checkpoint, stop and report instead of dispatching silently. Do not dispatch for normal implementation procedures, simple progress checks, or repetition of the same decision.

## Advisor evidence and current-target assessment

### Iteration, independent anchors, and requests

- Keep `iterative-confirmation` evidence separate from `independent-review` evidence, even when either reports `CLEAR`. Record the last independent review (including a non-`CLEAR` result), last independent `CLEAR` if any, and latest iterative confirmation as distinct evidence IDs with target, contract/epoch and actual coverage. Iteration never advances an independent anchor. A limited independent review advances only its covered scope; retain earlier anchors for untouched areas and evaluate interactions across them. No last-independent-`CLEAR` is fabricated when the first independent review finds defects.
- At completion, before push/PR when authorized, and after relevant corrections or adopted input changes, evaluate the direct cumulative change from the applicable independent anchors to the current candidate, not just the latest iterative delta. Advisor assesses findings and review assumptions; Coordinator assesses cumulative impact, execution contract and verification evidence. Use existing attributable Advisor assessments when they cover the current state; no separate polling dispatch is required at every milestone. Record both assessments with target/scope, rationale and evidence; an absent or stale assessment is unknown, not consent. Scope, meaning, dependencies, unresolved findings and evidence validity govern judgment; do not introduce fixed thresholds based on lines, files, or change category.
- If either Advisor or Coordinator requires re-independent review, or the user explicitly requests it, record requester, reason, target/cumulative scope and fulfillment evidence and perform it before final passage. Unknown is not `NOT_REQUIRED`: acquire the missing evidence or stop. A fulfilled request for the same target, reason and scope need not be dispatched twice; retain its record and evidence. An unfulfilled request cannot be dismissed as duplicate or overridden by the other actor's unnecessary assessment. New impact or changed scope reopens the assessment. Choose limited or full re-review based on the impact and dependency closure, without silently resetting uncovered anchors.
- Review necessity has no numerical cap, but dispatch is subject to the AI correction and checkpoint counters below. An ordinary iterative/re-independent review is not an additional decision checkpoint solely because it is another dispatch. `REVIEW_INVALIDATING` still advances epoch identity; epoch numbering alone is not the stop counter. Do not rename checkpoints or executions to evade a stop.

### Final assessment evidence

For `effective_review_level=ADVISOR`, Coordinator records a completed final assessment bound to the current target and epoch, with its outcome, evidence IDs and coverage. It has one of these bases, recorded as `assessment_mode`, unless an explicit applicable contract supplies the alternative final basis described under first-review exceptions below:

- `independent-current`: independent Advisor `CLEAR` for the current candidate with complete required scope and verified input/role isolation.
- `preserving-inheritance`: a verified append-only edge within the same epoch whose source revision already has a valid, completed final Advisor assessment or contract-permitted final basis. The edge identifies that source final-assessment record, its review kind, assessment mode, scope, independence evidence and completed-mode proof, and revalidates their applicability to the destination. Standalone iterative-confirmation, spot/slice `CLEAR`, and incomplete independent review are not eligible final-pass sources. A completed `current-target-confirmation` can be a source only with all its evidence requirements satisfied; its underlying iterative `CLEAR` alone cannot. A chain of preserving edges must remain traceable to a completed non-inherited final basis; a missing or ineligible source cannot be repaired by another preserving edge. Strict delta classification remains unchanged, and no source verdict is rebound to the destination.
- `current-target-confirmation`: a separate pass basis after an independent review and subsequent invalidating correction, including a review that originally returned findings rather than `CLEAR`. Record (1) independent evidence and scope anchors, source contract identities and applicability to the current request, (2) cumulative delta and impact assessment covering all changes and boundary interactions, (3) every finding's disposition with current correction/withdrawal evidence confirmed by Advisor, (4) sufficient current-target Advisor confirmation with actual read coverage, (5) Advisor and Coordinator reasons that no further independent review is needed and no unfulfilled requests or unknowns remain, and (6) successful current validation and all other required gates. These records may be concise linked evidence; no new universal schema is required. This is not inherited `CLEAR`, not independent review of the destination, and not an expansion of `REVIEW_PRESERVING`.

Independence is checked against the selected final basis: `independent-current` requires independent review of the current candidate; `preserving-inheritance` requires the eligible source final basis, its independence lineage and every preserving edge to remain verifiable; `current-target-confirmation` requires verified independent anchors and separately identified current confirmation, which may be non-independent. Do not claim destination independent review for the latter two modes. Unknown or missing required independence/evidence blocks passage; a non-independent confirmation allowed by the selected mode is not itself a failure of independence.

For withdrawal of an independent-review finding, record its ID, withdrawal reason and evidence, Advisor confirmation against the current candidate, and whether any unresolved issue remains. The original reviewer's assent is not a universal veto. Existing source-contract requirements for independent reconfirmation and unfulfilled independent-review requests still take precedence; withdrawal does not bypass them.

A first-final-candidate independent review is normally required. An exception must identify an explicit applicable authorizing contract/clause, target and scope, the independence obligation it replaces, its alternative final-pass basis and sufficient supporting evidence, and all remaining gates. Record and verify the alternative exactly as that contract permits; an exception label or a cost/size judgment is not evidence. If no complete alternative is authorized or its evidence is unverified, keep the gate blocked. Do not call it `independent-current` without actual current independent review, or `current-target-confirmation` without an actual independent anchor. This exception does not waive a mandatory lower bound or other approval/stop condition unless the applicable authority explicitly permits that change.

An invalidating change invalidates the old gate, evidence inheritance and authorizations as already specified. Re-resolve the new epoch's contract and Advisor triggers before choosing a final assessment basis. Historical independent evidence may be cited as an anchor in `current-target-confirmation`, never rebound to the new revision. Reverify its applicability: changes to scope, requirements, governance or execution conditions that leave a required area unreviewed or independence/evidence uncertain require additional evidence or re-independent review. The conditional route does not waive a source contract's fresh-review requirement, a mandatory decision checkpoint, explicit independent-review instructions, unresolved user decisions, or any other approval/stop gate. In particular, fix the pre-change source governance contract when editing these rules and judge that edit under it; the new route cannot approve its own introduction retroactively.

### Comparison and other review boundaries

- Git independent review normally uses a committed candidate; Implementer returns changes for Coordinator to commit. For an explicitly uncommitted target, use `advisor-review`'s immutable capture, including real-index/status/content/mode/ignored revalidation, and embed the complete declared primary scope plus required surrounding context and dependency closure. `mode=全文` requires full-file embedding; an excerpt in another mode must still cover its entire declared range and necessary evidence. Neither a live path nor the captured snapshot is a retrieval reference, and missing required coverage remains `NEEDS_EVIDENCE`. Compare each independent anchor directly to the current candidate with fixed base/target, complete delta and required context; intermediate revision records support traceability rather than replacing the cumulative comparison. For non-Git targets use fixed content snapshots/hashes, requirements and scope comparisons instead of forcing Git diff. Missing or changing content remains `NEEDS_EVIDENCE`.
- Content-identical squash/rebase is not itself a reason for re-independent review. Verify trees, range/diff, commit map, rollback units and post-operation validation separately, preserving history authorization and meaningful-topology gates. A remote update event alone does not trigger re-independent review or new remote monitoring. Evaluate necessary upstream changes after incorporation, or adopted requirements/contracts after they become review inputs; existing mandatory remote checks and explicit instructions remain in force.
- Issue #138's independent sequential code-review phases remain a separate contract: Phase 1 freedom from the checklist, Phase 2 after Phase 1 with the full base-to-candidate diff, separate initial contexts/findings, and Root's checklist non-reading boundary are not satisfied by an inherited Advisor. When that workflow is selected, complete its phases and required validation before fixing the final Advisor candidate; substantive Phase 2 corrections return through its Phase 1/2 rules and the lifecycle's revision classification. Neither its Clean result nor this Advisor assessment substitutes for the other's required gates. This does not activate an unimplemented or unselected code-review workflow.
- After corrections arising from the final Advisor, reassess the selected #138 workflow's review coverage and validation against the changed candidate. Return through its Phase 1/2 rerun rules wherever required, then fix the final Advisor candidate again. Advisor correction confirmation does not replace those reviews, and an old Clean result does not automatically cover the new snapshot.

## Spot review contract

- Spot review is a process in which the Advisor quickly checks the decision points, boundaries, and representative hunks with the highest risk in a read-only manner, rather than the entire change. It should not be made unconditionally mandatory based solely on the scale of implementation, but should be implemented when selected or triggered based on the contract, plan, or advisor necessity determination.
- The spot manifest records the spot ID, reason for selection, target file and hunk/stable anchor, primary scope, dependency closure, confirmation questions, verification method, advisor results, corrections made, and targets for re-review. Even if you do not select a target, record the risk assessment and `SKIPPED` reason.
- The spot advisor runs read-only, and the coordinator corrects the spot findings within the approved range. After modification, re-review the affected spots and dependency boundaries, and do not proceed to slice review until convergence. Spot `CLEAR` does not mean the completion of the final Advisor or user checkpoint.

## Review slice contract

- After implementation and planned builds/tests, before operational verification, divide the entire change into logical review slices. A slice is not equated with a commit, but is configured based on specifications/responsibilities, dependency closure, purpose of change, commit boundary, and boundaries with other slices.
- The slice manifest records the slice ID, purpose, target file and hunk/commit range, dependencies, cross-slice dependency/boundary edge, and verification method. In case of `effective_review_level=ADVISOR`, record the Advisor result and re-review target, and in case of `NONE`, record `SKIPPED` reason for Advisor review.
- Each file/hunk/commit of all changes belongs to at least one slice, and cross-slice dependencies and boundary edges are specified in the review context of one of the slices. If there are coverage gaps, overlaps, or undefined boundaries, mark `BLOCKED` and do not mark the review as complete.
- In the case of `effective_review_level=ADVISOR`, slice Advisor fixes the primary scope and dependency closure of each slice and executes it as read-only. The coordinator makes corrections within the approved scope and re-reviews the corresponding slice and dependency boundaries. Do not proceed to final review or autosquash until all slices have converged. ### Revision and review-preserving classification

- `revision_identity` represents the target identity, tree or snapshot, target range, and is updated every time the content or topology changes. `advisor_review_epoch_id` stands for review contract, scope, dependency closure, assumptions, role, environment, governance version, and reviewed anchor, and is not the same as revision.
- The coordinator is the sole decision-making body for `review_delta_classification`, and records in the ledger the from/to revision, complete delta manifest and hash, category, classifier identity and reason, behavior, contract, scope, dependency, security, data, compatibility, rollout, rollback, and governance impact axis true/false/unknown and basis, validation, source evidence ID, inheritance edge ID, and epoch. Self-declaration of implementer or author alone does not confirm the decision.
- For `REVIEW_PRESERVING`, all impact axes recorded above (`behavior`, `contract`, `scope`, `dependency`, `security`, `data`, `compatibility`, `rollout`, `rollback`, `governance`) are definitively false, and it can be verified that existing review contracts, permissions, dependency boundaries, and audit ledgers will not change. If any axis is true or unknown, evidence is lacking, the ledger is absent, hashes mismatch, or verification is impossible, set `REVIEW_INVALIDATING`.
- The preserving allowlist for normative documents is limited to end-of-line/trailing-whitespace normalization that leaves semantic tokens and structure unchanged, or typo/finding fixes that satisfy the exact old/new and definitive resolution predicates in existing findings. General labels such as comment, format, mechanical, and non-normative do not make a change preserving; classify it as invalidating unless an explicit, definitive marker/predicate says otherwise.
- Changes to `behavior`, `contract`, `scope`, `dependency`, `security`, `data`, `compatibility`, `rollout`, `rollback`, `modal`, `quantifier`, `negation`, `gate`, `role`, `state`, `category`, `reference path`, `review contract`, or governance, as well as changes to this Skill's own rule/schema/allowlist, must be `REVIEW_INVALIDATING`. Even if the same actor serves as both classifier and author, invalidate unless the deterministic allowlist and predicate are satisfied. When classifying these changes and selecting the required Advisor assessment, fix the source contract manifest (paths, blob/OIDs, and hashes for this Skill, `link-targets/agents/AGENTS.md`, `link-targets/agents/skills/advisor-review/SKILL.md`, `link-targets/agents/skills/delegation/SKILL.md`, and their required dependency closure) and its hash from `from_revision`; do not evaluate yourself under the destination's post-change rules. Preserve any fresh independent dispatch required by that source contract. If the source contract cannot be fixed, stop at `NEEDS_EVIDENCE`.
- Coordinator asks for `from_tree = git rev-parse <from_revision>^{tree}`, `to_tree = git rev-parse <to_revision>^{tree}` for committed target.
- For uncommitted target, first capture the absolute path and raw SHA-256 of the real index, the real-index/worktree byte stream of `git --no-optional-locks status --porcelain=v2 -z --untracked-files=all`, the index entry byte stream of `git --no-optional-locks ls-files --stage -z`, and the ignored-path byte stream of `git --no-optional-locks ls-files --others --ignored --exclude-standard -z` without changing the real index. Next, create new dedicated `GIT_INDEX_FILE` and dedicated `GIT_OBJECT_DIRECTORY`, read `from_revision` with `git read-tree`, fix the candidate manifest, apply each entry to type-aware, and create an immutable `to_tree` with `git write-tree`. After capture, return to the real index and reacquire the status/index/ignored/manifest of the same `--no-optional-locks`, and if there is a difference in the index hash, raw status, path set, and content/mode hash of each entry, discard the capture and make it `REVIEW_INVALIDATING` / `NEEDS_EVIDENCE`.
- The candidate manifest is fixed in the order of Git's NUL byte path, and each entry records path bytes, mode, source state (`FROM`, `INDEX`, `WORKTREE`, `UNTRACKED`, `DELETE`, `IGNORED_EXCLUDED`, `GITLINK`), source blob/OID, raw content SHA-256, size, and symlink target bytes. Entries whose working tree differs from index are `WORKTREE`, entries whose only index differs from from_revision are `INDEX`, new entries are `UNTRACKED`, deletions are `DELETE`, and `MM` uses working tree bytes and also records index bytes. mode `160000` records the complete gitlink commit OID of from tree, real index, worktree HEAD and the clean/modified/untracked/unmerged/unresolved status of submodule as a non-blob `GITLINK` entry. The unchanged gitlink leaves the mode `160000` and OID maintained by `git read-tree` in the candidate tree, and does not apply raw content SHA-256, size, symlink target, and `git hash-object` to submodule directory bytes. gitlink OID or mode changes, modified/untracked/unmerged state of nested worktree, or unresolvable OID/status will fail-close as `REVIEW_INVALIDATING`/`NEEDS_EVIDENCE` before candidate tree generation and raw delta calculation. Raw bytes other than `GITLINK` are passed to `git hash-object --no-filters -w --stdin` in the environment of `GIT_OBJECT_DIRECTORY=<private>` and `GIT_ALTERNATE_OBJECT_DIRECTORIES=<repo-objects>` that reads the repository object database without clean filter, quote, line break conversion, or normalization, and distinguish between the output Git blob OID (object format of `git rev-parse --show-object-format` is also recorded) and raw SHA-256. For dedicated index, apply blob OID equivalent to `git update-index --add --cacheinfo <mode>,<git_blob_oid>,<path>` instead of raw SHA-256, and for deletion, apply equivalent to `git update-index --remove`. Perform `git write-tree` within the scope of the dedicated object database and do not change the ref, real index, or working tree.
- Next, only after proving with gitlink preflight that the from/to gitlink OID is unchanged and the nested status is clean, execute the fixed option `git diff --raw -z --no-renames --no-ext-diff --ignore-submodules=all --abbrev=40 <from_revision> <to_tree>` to convert the stdout byte stream to SHA-256 without decoding, quoting, line break conversion, or normalization, leaving it in Git path order and NUL delimited. `--ignore-submodules=all` is not proof of gitlink immutability. The complete `to_tree` is the main identity, the raw bytes delta hash with SHA-256 is the supporting evidence, and any mismatch in the tree, real-index/status snapshot, candidate manifest, blob OID, or hash is invalidating.
- When reusing Advisor evidence with preserving, add append-only `review_evidence_inheritance` edge and record source evidence, source revision, destination revision, delta manifest/hash, category, classifier/reason, impact axes, validation, and epoch. Do not reassign the verdict of the source to the destination or copy the evidence.
- The packet, child context, and reviewer judgment remain bound to the source revision, and if the revision changes, they are not blindly reused even if they are preserved, but are reacquired if necessary. If the ledger cannot be verified in the current execution context, inheritance will not be performed. Do not promote a previous `BLOCKED`, `NEEDS_EVIDENCE`, or any other non-`CLEAR` verdict to `CLEAR` solely on the basis of a `REVIEW_PRESERVING` classification.
- `REVIEW_PRESERVING` can only suppress redundant Advisor dispatch for the same epoch, and does not exempt `effective_user_review=REQUIRED`, commit map, lifecycle gate, or external operation authorization. When measuring the reduction in the number of Advisor dispatches, only Advisors are counted.

## Commit unit

- The coordinator makes semantic commit decisions and Git operations. Implementer returns changes and validation results; Advisor does not perform a commit operation.
- The default is to make a commit a single consistent, reviewable, and revertable intent. Don't split just because of files or layers.
- The target implementation and the tests necessary for its verification are not mechanically separated. Even when separating artifacts from their sources, prioritize project-specific generation procedures and dependency orders.
- `Commit map` is required in the plan when multiple independent functions, independent rollback units, DB additive change/backfill/switching, compatibility development of multiple services, complex correspondence between generation sources and products, or cases where the fixup destination is ambiguous are required. The map describes the identifier of each unit, intention, target file (change range for shared files), dependency order, verification method, rollback range, expected first commit, and fixup target. It is not necessary to write a fixed phrase every time it is a simple task, but if you cannot determine the applicability, please check with the user.
- When reviewing a fixed commit, first create an initial implementation commit. fixup targets the corresponding implementation commit. Amend requires explicit plan/user approval naming `amend` and its target, or every condition of the kernel's unpublished-task-commit rewrite exception; record the evidence. “Maintain one logical commit” alone is insufficient. This does not grant Git writes to an Implementer.
- For complex plans, check the commit map against the actual commit range before starting the review. Stop if a unit does not correspond to a planned commit or specified commit group, if changes to target or shared files are unassigned or overlap, or if the dependency order, verification method, rollback range, or fixup target do not match.
- The commit range owned by lifecycle fixes the base / start boundary at the start of execution, the order of commits created by the coordinator, termination candidates, and exclusion of existing commits and unrelated concurrent changes to the range manifest. Do not run fixup / autosquash if you cannot reproduce the range identity or if it crosses the ownership boundary.

## Review status

When Advisor is executed, it returns one of the following. Do not confuse it with the necessity determination before execution `REQUIRED`, `NOT_REQUIRED`, `UNRESOLVED`.

- `CLEAR`: Issues requiring judgment have been resolved, and there is no advice to block the gate.
- `REQUIRES_USER_DECISION`: Users must decide on planning, scope, and risk acceptance.
- `BLOCKED`: Advisor execution, evidence, or target identity cannot be established.

### Status axis and user permissions

Record the findings, evidence status, review gate, and permission to proceed with implementation separately. The definitions used in the implementation gate are as follows.

- `finding_outcome`: Either `指摘成立` or `指摘撤回` for each Advisor finding. Issues for which the Advisor requires user judgment are recorded as `REQUIRES_USER_DECISION`, and cases where evidence or target identity cannot be established are recorded as `BLOCKED` on a separate axis.
- `evidence_status`: `SUFFICIENT` or `NEEDS_EVIDENCE`. The latter is an incomplete state caused by missing information, missing target identity, or non-reproducibility; normally `review_gate=BLOCKED`. Record the necessary evidence, confirmation method, scope of permission, and termination conditions, and do not consider it as a retraction or approval of the points raised.
- `review_gate`: One of `PASS`, `PASS_WITH_USER_AUTHORIZATION`, or `BLOCKED`. Use plain `PASS` only when there is no unresolved `NEEDS_EVIDENCE`, no gate-blocking finding, the selected final basis's required independence evidence is verified as specified above, and the normal completion conditions are met. If work proceeds with `NEEDS_EVIDENCE` left unresolved and only within scoped permission, use `PASS_WITH_USER_AUTHORIZATION` and do not convert it to plain `PASS`. Use `BLOCKED` if requirements, target identity, or authorization are insufficient.
- `USER_AUTHORIZED`: Explicit user permission recording that does not override finding status or evidence sufficiency. It includes the finding ID, target/epoch and manifest, authorizer, date and time, source, scope of operation and exclusions, accepted impact, remaining confirmations, and deadline or reverification conditions.
- `proceed_status`: `STOPPED` or `AUTHORIZED_TO_PROCEED`. Set the latter only if a valid `USER_AUTHORIZED` is bound to the same target/epoch and operation scope.

`ACCEPTED_RISK` is a note of acceptance, not a permit to proceed. References to the old `WAIVED` may be retained, but new records must use it only to mean that specific evidence or checks were waived; the finding must not be treated as cleared.

## Execution order

### 1. Fixed, implemented and planned verification of execution contract

Fix the contract, target manifest, exclusion range, epoch, starting boundary of lifecycle-owned range, and review contract from the plan or finalized execution input. Do not stop just because there is no plan or changes span multiple files, but stop if the goal, scope, constraints, completion conditions, or verification method cannot be uniquely determined.

The implementer makes changes and verifications within the scope of the contract, and the coordinator creates a semantic commit. Run the planned builds/tests and generated-artifact verification. Record each command, exit code, result counts when available, and full-output location. Apply the runtime decision table to deviations, estimate excess, and runtime design choices before the affected operation. Don't let Implementer or Advisor do commit/fixup/amend/autosquash.

### 2. Spot review (when selected)

If you select or trigger spot review, after implementation and initial planned validation, pin the spot manifest to have the Advisor review read-only high-risk/representative areas. If any issues are found, the coordinator will correct them and re-review the affected spots and dependency boundaries. If spot is not selected, record the rationale and `SKIPPED` reason why the selection condition is false in the ledger. Spot review is not a substitute for full change coverage, slice review, user checkpoint, or final review.

### 3. Review slice configuration, Advisor review (when selected), and modification

After implementation and planned builds/tests, before operational verification, create a slice manifest and assign all changes to review slices. Fix the primary scope, dependency closure, cross-slice dependency/boundary edge, and validation method for each slice to ensure that there are no coverage gaps, overlaps, or undefined boundaries.

In the case of `effective_review_level=ADVISOR`, each slice is reviewed by the Advisor as read-only, and the coordinator records corrections as `fixup!`, an authorized `amend` under Commit unit, or a new commit. Re-review affected slices and dependency boundaries until converged. Slice review does not substitute for final review or user checkpoint. For `NONE`, record why all required Advisor triggers are false and the slice Advisor's `SKIPPED` reason.

### 4. Operational verification and candidate organization

Run planned operational verification after slice convergence; correct gaps with fixups and rerun affected verification/reviews. Autosquash under the lifecycle rules, then fix the final candidate's base SHA, tree/commit identity, hunk and commit map. Detailed review precedes selected user review.

### 5. Determining review strength

Immediately after fixing the candidate target, confirm `effective_review_level` by matching `requested_review_level` with the required trigger. `effective_user_review` inherits the value resolved by preflight, and even if the selected value is `NONE`, if there is a mandatory Advisor trigger, the lower limit on the AI review side will be applied. If Advisor is not included, record the reason, basis, and contract of the user or goal for making the review `SKIPPED` in the ledger. `SKIPPED` does not imply completion of verification, selected regular review, or approval.

### 6. Final Advisor judgment

Before user review, reverify epoch identity and provide the fixed plan/input and target. For `effective_review_level=ADVISOR`, normally obtain independent review for the first final candidate, with an exception only under the explicit first-review exception requirements above; for subsequent candidates record the current-target assessment basis. A required trigger remains `REQUIRED`; stop on `REQUIRES_USER_DECISION` or `BLOCKED`, including during one-shot delegation. If Advisor cannot run for `UNRESOLVED`, stop and report. For `NONE`, verify all triggers false and record `SKIPPED`. Obtain Codex detailed review under the review contract as well. Neither Codex nor user approval nor checkpoints replace the final Advisor assessment.

### 7. Correction of indications

- All `指摘成立` findings block the gate and are corrected by the coordinator within the approved range. If the user must decide whether a correction is necessary or whether to accept the risk, stop with `REQUIRES_USER_DECISION`. Do not let the Advisor make changes or commits. To proceed without changes, obtain a separate `USER_AUTHORIZED` record containing the finding ID, target/epoch, scope, accepted impact, remaining confirmation items, deadline, and reverification conditions. Apply `proceed_status=AUTHORIZED_TO_PROCEED` and `PASS_WITH_USER_AUTHORIZATION` only to the recorded range. A bare `ACCEPTED_RISK` note or legacy `WAIVED` is not authorization to proceed.
- After modification, execute planned build, test, and generation verification; autosquash and return to detailed review. Apply the runtime decision table to deviations, estimate excess, and runtime choices.
- After modification, fixup, or amend, the changed snapshot must be determined by `review_delta_classification`. `REVIEW_INVALIDATING` starts a new epoch and settles a new review contract without reusing the regular review results of the old epoch. For `REVIEW_PRESERVING`, epochs can only be maintained through inheritance of Advisor evidence, and regular reviews for `effective_user_review=REQUIRED` will be performed as per the contract. Regular review of `NONE` updates `SKIPPED` record, but packet, context, and judgment are not automatically inherited.
- Record the fix as a fixup to the corresponding implementation commit; amend follows the conditional authorization in Commit unit above.

### 8. New review epoch

Modifications, fixups, amends, history cleanups, or meaningful epoch-identity changes classified as `REVIEW_INVALIDATING` start a new epoch by revalidating the target manifest, SHA, plan identity, and epoch identity. Re-resolve the review contract; do not reuse old user review or gate/verdict. Verify, autosquash, and complete detailed review with a new current-target assessment before selected user review; `NONE` updates its `SKIPPED` record.

Be sure to re-evaluate review contracts and Advisor necessity triggers in new epochs. The `REVIEW_INVALIDATING` target does not reuse the previous `NOT_REQUIRED` or final Advisor verdict. If Advisor is required or included in `effective_review_level`, choose `independent-current` or, where its evidence conditions and applicable source contract permit, `current-target-confirmation`; any explicitly authorized first-review exception must satisfy its own complete final-basis requirements. Refresh the request and evidence for the new epoch; never resume the old epoch's handle or replace source evidence with a destination verdict. For final-pass `REVIEW_PRESERVING` inheritance, verify the source's already completed eligible final assessment and independence lineage, same epoch, complete delta manifest/hash, append-only edge, and ledger in the current context. Record the source final-assessment ID, mode, evidence and scope, `assessment_mode: preserving-inheritance`, old/new target, comparison and cumulative checkpoints. Bare source `CLEAR` is insufficient. Discrepancy, unknown identity, incomparable content, changed contract/premise/scope/normative meaning, incomplete source final basis or missing required independence evidence prevents final-pass inheritance. Historical review and findings can still be anchors for a separate, fully evidenced current-target assessment. Do not copy old `NOT_REQUIRED`, `CLEAR`, or `SKIPPED` to the new target.

### 9. User normal review (if selected)

After detailed reviews converge, present the final candidate and verification results for `effective_user_review=REQUIRED`. Record snapshot identity, presentation, explicit approval/no-change response or confirmation resolving each feedback item, and absence of unresolved feedback. If topology matters, include it in the presented target. For `NONE`, record the reason, basis, and designation source of `SKIPPED`. When `agent-pipeline-guardrails` applies, obtain and record the user's production-adoption decision at this same stage, separately from review completion; review results are not that decision.

A scope/design-changing rejection returns to planning and approval. Otherwise correct, verify, autosquash, and repeat detailed review before renewed selected user review. Apply the counter-reset rule in Stop/confirm conditions to candidate feedback; old target evidence does not become valid for the corrected candidate.

Preserve history authorization and the kernel's conditional rewrite exception. Do not let Implementer or Advisor perform autosquash.

## Completion conditions

The gate is set to plain `PASS` or `PASS_WITH_USER_AUTHORIZATION` with valid scoped authorization attached to unresolved `NEEDS_EVIDENCE` only when all of the following are satisfied. The latter is limited to the recorded operating range.

- The plan or execution contract identity, approved scope, target manifest, final target, and epoch identity revalidated just before finalization match.
- The verification specified in the plan or contract is successful.
- If spot review is selected or triggered, all targets in the spot manifest are `CLEAR` or have been re-reviewed after modification. If not selected, the rationale and `SKIPPED` reason why the selection condition is false are recorded.
- Coverage of slice manifest is complete. In the case of `effective_review_level=ADVISOR`, Advisor reviews for all slices and cross-slice dependency/boundary edge have converged. For `NONE`, all required Advisor triggers are false with a rationale, and the slice Advisor's `SKIPPED` reason is recorded.
- In the case of `effective_user_review=REQUIRED`, it can be confirmed in the ledger that the user-review snapshot linked to the final candidate target, the presented content, the user’s explicit approval or confirmation of no changes, or responses confirming feedback resolution, and the absence of unresolved feedback. In the case of `NONE`, you can check the reason, basis, and designation source for setting the normal user review to `SKIPPED` in the ledger.
- If `effective_review_level` includes Advisor, the completed final assessment satisfies one of the defined modes or a complete alternative expressly authorized under the first-review exception requirements. All mode-specific independence evidence, required independent requests and current identity/evidence are verified. Preserving inheritance has an eligible completed source final basis, not merely source `CLEAR`. `current-target-confirmation` is a new current-target basis even after `REVIEW_INVALIDATING`, not a claim of destination independent `CLEAR`. If Advisor is omitted, all required triggers are false with a rationale and the reason for `SKIPPED` is recorded.
- The additional Advisor checkpoints in the current allowance are no more than two; reasons, decision questions, targets, results, and any reset basis under the counter-reset rule in Stop/confirm conditions are recorded.
- The initial commit and fixup/amend/autosquash ranges consist only of lifecycle-owned range changes approved in the plan or contract. If autosquash is executed, record the tree identity, topology, range / diff, and post-verification before and after, and if not execute, record the `SKIPPED` reason.
- In a plan that requires a commit map, the actual commit/hunk manifest and the map are fully matched in both directions, and all commits/hunks are assigned to exactly one unit, and there are no changes or duplications that are not in the map. Independent rollback units are separated at commit boundaries, and when they are combined into the same commit due to dependencies, the reason and joint rollback range are recorded in the map.
- Detailed AI reviews precede selected user review of the final candidate, and all established Codex findings have recorded dispositions. Before the completion-state operation, selected Codex review must be complete or explicitly omitted under the review contract.
- Record the agreed completion state and outstanding operations separately from gate PASS. Obtain each required implementation-adoption, history, or external authorization; a task is `COMPLETED` only when that state is achieved and verified.

After plain `PASS` or `PASS_WITH_USER_AUTHORIZATION`, be sure to classify the differences in revision. `REVIEW_INVALIDATING`, meaningful differences/indiscernibility/incomparability in epoch identity (plan or execution contract identity/approval status, exclusion range, effective model/role/inference budget, permission/sandbox, routing, tool/plugin settings/availability, or gate control file fixed to review (`AGENTS.md`, `SKILL.md`, agent definition version)), a change in the review contract, or, when `effective_user_review=REQUIRED`, a change in the snapshot, presentation content, response, unresolved feedback, or approval status (including new feedback, unresolved feedback, or approval withdrawal) invalidates the gate status and review-derived `USER_AUTHORIZED` / `PASS_WITH_USER_AUTHORIZATION` / `proceed_status`, revalidate the target identity, exclusion range, epoch identity, and normal review evidence and start a new epoch. The authorization boundary itself is re-evaluated under the independent `external-operation-authorization` contract, and if the boundary remains unchanged, authorization records can be maintained, but no external operations will be performed until a new review/verification is completed. Authorization itself is invalidated only when the boundary has changed, expired, or cannot be confirmed. In the case of `REVIEW_PRESERVING`, `USER_AUTHORIZED`, `PASS_WITH_USER_AUTHORIZATION`, retry/consumption status is not inherited to the new target, and only inheritance and physical verification of Advisor evidence is allowed. If the basis for designation of `effective_user_review=NONE` changes, it will be treated in the same way. Unrelated changes to the environment or the shaping of semantic equivalences are excluded only when it is possible to record a basis that does not affect the fixed target and normative meaning. Squash and rebase are treated as separate operations, and the target identity, classification, and difference are verified after execution.

## Stop/confirm conditions

In the following cases, the process will not continue automatically and the status, evidence, remaining findings, and next options will be reported to the user.

- Two evidence-based fixes to the same AI finding have failed, or a further AI-driven `REVIEW_INVALIDATING` correction would begin the third counted epoch. Initialize the AI correction counter at 1 for the first epoch; increment for invalidating Advisor/Codex corrections, not user rejections. Counter-reset rule: outside one-shot delegation, a user instruction containing a correction to the candidate's content counts as a substantive rejection, including after a stop and when `effective_user_review=NONE`; reset the AI correction counter to 1, same-finding failed-fix counts to zero, and the two-checkpoint allowance. Bare or ambiguous continuation does not reset; no reset occurs while one-shot delegation skips user review. Epoch identifiers continue increasing independently. Trigger 7 does not lift the stop; do not reclassify an execution to evade it.
- Scope/identity, target manifest, fixup target, or lifecycle-owned range is no longer unique, or an estimate/decision reaches a stop in the runtime decision table.
- Existing dirty diffs cannot be safely excluded, the target changed during review, or build/test/generation verification failed.
- A required or selected spot review has not been performed or has not been converged, there is a gap/overlap/undefined boundary in slice coverage, or the review context of cross-slice dependency cannot be fixed.
- `effective_user_review=REQUIRED` but the user normal review of the epoch has not been completed, there is no snapshot-linked explicit approval or confirmation that no changes were requested, or confirmation that feedback was resolved, unresolved feedback remains, an additional Advisor checkpoint returned something other than `CLEAR` (including `BLOCKED`), or a third additional Advisor checkpoint is required. In the case of `effective_user_review=NONE`, it also stops when the basis for `SKIPPED` cannot be recorded.
- The input source/value for `user_review` or `review_level` is unknown, conflicts with a required Advisor lower limit, or cannot record the rationale for assigning the selected review to `SKIPPED`.
- The Advisor requested user judgment; the selected final basis's required independence evidence or ledger authenticity cannot be confirmed; an eligible completed source final assessment for preserving inheritance or an exception's authorized alternative basis cannot be verified; a `指摘成立` finding remains; or the scope, deadline, or target/epoch of valid `USER_AUTHORIZED` corresponding to `NEEDS_EVIDENCE` cannot be confirmed. A permitted non-independent current confirmation is not presented as missing destination independence; verify the actual requirements of its selected basis.
